# 支付基础验证与配置边界

开发基线为 develop `6938bd7`，PR86、PR87 已按用户批准顺序合并，其合并后 CI 已成功。开发在独立 worktree，不修改原目录的用户改动。

## 本轮可验证

1. 使用真实 USER/ORDER/SCH 本地事实创建订单和内部支付意图，付款单始终使用固定业务编号。
2. 使用测试进程生成的 RSA 2048 密钥，对原始回执字节按官方三行规则签名，再经生产验签代码接收。
3. 验证 PAYMENT 记录与 PaymentSucceeded Outbox 一起提交/回滚，真实 dispatcher 消费后 ORDER 与 SCH 一起进入待商家确认/正式占用。
4. 注入重复通知、修改金额/对象、错误签名、错误数据源、故障和迟到支付，核对没有重复成功事件、重占预约或伪造退款成功。

这不是拉卡拉联网联调或微信真机付款验收。测试 merchant_no/term_no/AppID 均为本地 fixture，测试钥匙不得进入运行配置或版本库。

## 内部装配

`pet.payment.foundation.enabled` 默认 false；装配依赖已有预约保护、内部订单创建、订单到期能力和 Outbox。即使显式启用，也没有新增消费者发起支付/外部回调 HTTP 路由。

服务端绑定配置形状如下，示例仅为字段说明，不是可用商户参数：

```yaml
pet:
  payment:
    foundation:
      enabled: false
    lakala:
      channel-time-zone: "<向渠道核实后填写，不能沿用测试假设>"
      notification-certificate-path: "<X.509通知公钥证书的本地路径>"
      stores:
        "<门店ID>":
          merchant-id: "<平台商家ID>"
          merchant-no: "<拉卡拉商户号>"
          term-no: "<拉卡拉终端号>"
          sub-app-id: "<该收款方案关联的小程序AppID>"
```

缺绑定时内部 prepare 返回依赖不可用；缺通知公钥或渠道时区时通知入口不能写入支付成功。没有内置默认收款商户、私钥或自动生成的生产凭据。证书明确配置但无法读取时启动失败，错误不输出证书正文。

SQL40 仅隔离库执行；历史记录不自动补商户、币种、支付身份或 cancel_reason。未来正式接入须先核实渠道时间时区、营销实付金额与退款映射，以及原截止时间和短期参数的关系。退款执行、自动接单、券消费和通知消费者仍需后续交付。

最终本地/远程验证证据及未交付项见本轮 PR。代码默认关闭，合并与生产启用需另行批准。
