## 交付行为

- AFS 内部命令覆盖资格、创建、受理、补证、商家意见、撤回、重复问题关闭和一次终局裁决；同单最多一笔活动工单，与普通待处理/已批准待建单申请双向互斥。撤回后重新申请沿用原资格与原七天窗口。已核销窗口取真实 `verifiedAt`，未核销窗口取预约开始且要求真实普通退款拒绝，七天截止包含等号。
- 既有非退款终局后的新问题由用户补充新事实，运营受理须核对服务端完整历史集合及版本。重复问题仅关闭并引用原决定，不生成第二次决定、退款或复审。补证截止与申请七天是独立规则：指定方须在截止前提交，超时任务只恢复处理中状态。
- 真实 USER / ADMIN_WEB 会话、当前 RBAC 与商家门店范围接入；已成功请求重放仍核验原动作的当前权限和输入绑定，随后返回原首回执，不重新依赖内容审核或原因目录。运营决定持久绑定 `authzVersion` 与真实 `scopeVersion`，提交前复验。
- 私有证据使用独立 `AFTERSALE_EVIDENCE` 用途、真实上传/扫描就绪事实和不可变批次。typed 读取授权绑定工单、批次、资产、对象版本、主体及会话；一次消费、读取审计、水印和返回前复验均独立实现。对象读取和内容审核位于业务事务外。
- FULL/PARTIAL 决定与实际 `refund_order`、三域来源证明、ORDER 投影、任务、事件及首回执在同 DataSource 的可写 RC 短事务内提交。核销先成功即使原未履约工单失效；退款单先创建即禁止核销，包括渠道 UNKNOWN/FAILED。核销同时取消开放补证轮，保留真实核销完成证明。历史核销回执不受后来合法新工单指针影响。
- PARTIAL 精确绑定真实原付款与运营金额，旧迟到/拒单/普通来源继续只允许 FULL。PAYMENT 首发前核对 AFS、ORDER、REFUND、付款与资金权威；`MAY_HAVE_SENT` 后仅查原退款号。真正成功后同事务更新 ORDER 金额、去重 claim 并释放原预约，两类履约阶段均保留真实核销历史。既有消费者按来源分派，未知来源失败关闭。
- 持久补证任务从真实 worker 的 `TaskInvocation` 获取调用上下文，核对任务元数据；伪造 SYSTEM DTO 不能触发超时。缺失/终态任务可按原 key 恢复，坏来源隔离记录，不抢占运行租约。任务上下文不代表另外实现了逐操作租约版本栅栏。

## 实际验收记录

本地使用 Java 21、MySQL 8.4 独立实例 `127.0.0.1:3315`、随机 QA schema 和独立 Redis `127.0.0.1:16385`，Maven 串行。仅测试库应用 SQL50，未执行生产迁移。完整命令及报告在本聊天工作产物目录，最终逐类结果以 `actual-summary.json` 为准；矩阵映射见 `EXECUTED-TEST-MAPPING.md`，资金专项见 `MONEY-TEST-MAPPING.md`。

第一轮新增用例运行发现 PAYMENT 成功事实仍强制退款额等于实付，误拒合法 PARTIAL 的成功收尾；已改为合法正金额且不超过实付，同时保持签名回执金额与 dispatch 精确一致、旧来源创建/执行 FULL 限制。第一轮 Money 12 项中 3 项因此错误，不能计为通过；修复后的定向复测与最终 CI 必须独立记录。测试源码存在不等于已经执行，后续报告覆盖本段历史失败。

本地新增 82 项在增量批次及修复复测后均已有通过证据；不是单次全量运行，也不将历史失败隐藏为一次绿色。第二轮跨订单用例的准备时钟与继承下单保护时钟不一致，导致在售后断言前被既有排期保护拒绝；仅修正 fixture，在首单预约结束后用统一受控时钟创建第二笔真实订单，定向复测通过。生产规则未放宽。

最后交叉审查另发现首次 preflight 用历史时间验证资金有效期的 P1：MAY_HAVE_SENT 提交后若暂停至授权过期，旧代码仍会调用渠道。新增确定性用例在真实 dispatch commit 后推进到 validUntil 等号，旧代码稳定失败；修复后首次 preflight 末尾按当前 DB 时间拒绝过期授权，历史查单仍使用原授权时点，不重建证明或重发。该用例及资金/原号恢复/旧PAYMENT/架构共52项修复回归全通过。旧提交 `75a1caf` 的 CI36681010671 主动取消，不算全量通过；以修复后 PR97 当前 head 的 CI 为准。

提交 `f55fb14` 的 CI36682136380 在旧 ORDER 组件测试停止，实际 46 份报告、337 次执行中 1 error；其他五项检查通过。原因是旧 `OrderVerificationHistoryMySqlTest` 未提供新增的 AFS 历史证明依赖，初次正向读取就失败，并使两个旧拒绝用例失去有效性。修复仅调整该组件 fixture：显式提供绑定订单/门店/核销/时间/数据源的历史测试端口，先证明正向可读，再验证历史快照和叶子证据损坏会拒绝。当前售后指针可以合法变化，不再被误当成历史证明损坏。该组件仍采用测试种子，真实工单/核销链证据由独立 BOOT 验收承担；本次失败不计为全量通过。修复后该类 4 项定向复测全部通过（其中 1 项为旧类新增方法，单独记录，不混入上述 11 个新类的 82 项）。

1. OD-W0-001 的真实可退资金/分账权威 Provider 及从查验到出款间的真实并发保证未交付。本批只交付失败关闭的公共协议及 test-only provider 验收；PAID 或无分账记录不构成可退证明。不得据测试替身启用生产退款。
2. 内容安全、渠道、微信/验证码上游及对象存储的受控适配在测试中披露；本批没有真实资金操作、真实渠道/OSS/扫描器部署验收。生产必须显式提供真实审核器、批准原因目录、保护密钥和资金权威；无恒真默认适配。
3. AFS 公开 HTTP、运营/小程序页面、STAFF 绑定授权、真机与完整端到端尚未交付。通用现有上传 HTTP 没有因增加内部用途而公开 AFS 上传；OpenAPI 对应售后操作明确标记 INTERNAL_ONLY。
4. 实际通知送达、评价/积分/优惠券消费者和重新服务的第二次预约自动化不在本切片。Outbox 只证明可靠意图，不等于用户已收到通知或下游结算完成。
5. 逐故障注入、幂等、权限和竞争的实际覆盖以测试映射为准；没有把准备矩阵中所有场景都宣布通过。完整 AFS-001/002、VER-002、QA-004 及相关退款 Issue 继续保留未验范围。

## 默认关闭与回退

`pet.aftersale.enabled`、`refund.enabled`、`worker.enabled`、`http.enabled` 均默认 false；依赖开关和真实适配缺失则启动或操作失败关闭。HTTP 尚未实现，打开该开关会被明确拒绝。关闭新退款准入后，已提交退款仍必须保留原号查询和恢复能力。

SQL50 为显式增量而非启动自动 DDL；未知历史来源预检失败，不猜测回填或清空历史。生产启用需另行迁移/适配/运行验收；已有新来源事件后不能退回仅理解旧来源的消费者。此 PR 不合并 develop/main，不自动发布。
