## E01 大 ID 与金额（ORD-011 / W2-IDEM-001/002）

合法传输样本：`{"orderId":"9007199254740993","refundId":"9223372036854775807","amount":"128.00"}`。ID逐字符往返不变。反例`{"orderId":9007199254740993}`在进入规范化前拒绝，不能先转Number再转String补救。上界+1的`"9223372036854775808"`、`"01"`、负ID建议拒绝（新Codec规则待批）。

Money建议样本：`"128"`/`"128.0"`/`"128.00"`→`"128.00"`，`"9999999999999999.99"`可表达；`"10000000000000000.00"`、`"128.001"`、`"128.000"`、`"1e2"`、`128.00`、`"-0.00"`拒绝。负数/零还须具体业务准入；这不是退款金额规则批准。

## E02 精确规范字节（W2-IDEM-004）

示范命令`review-fixture.accept`只用于本Markdown，不注册产品API。schema明确三个业务字段amount、appointmentStart、serviceId，均必填，其他字段拒绝。输入对象键顺序不同、amount=`"128.0"`且时间=`"2026-09-14T14:30:00+08:00"`时，按建议canonical-v1得到以下**一行、无尾换行**：

```json
{"amount":"128.00","appointmentStart":"2026-09-14T06:30:00.000Z","serviceId":"9007199254740993"}
```

UTF-8长度 **96 bytes**；SHA-256：`70a26b6513ac06a832a4f6e3cb879ac7d954f94f984bf38041da1ce1f35fdea9`。复核方法：复制代码块内部整行、不含换行，以UTF-8编码后算SHA-256。2026-09-14实际用PowerShell/.NET UTF8与SHA256核得上述值；仅证明样例字节正确，不证明Java组件已实现。

参数serviceId改为`"9007199254740994"`必须与原规范字节不同；traceId改动不参与。通用例子：`{"a":null}`与`{}`不相同；`["1","2"]`与`["2","1"]`不相同；`"理由"`与`" 理由"`不相同；时间同一Instant的+08:00与Z可同值，未定义默认值/无序数组不能擅自合并。旧canonicalVersion必须保留解释能力，不能按新版重新算后覆盖旧摘要。

## E03 同参重放/异参（ORD-013基础 / W2-IDEM-003/004）

固定终端header `X-Request-Id: 11111111-1111-4111-8111-111111111111`。用`R`简写该合法UUID，绝不把`A`或工程fixture的internal-write-001当终端UUID格式。

S = `(order.create, USER, "101", consumer-domain, R)`，业务P含serviceId=`"1"`及该命令未来获批全部必填字段。首次成功回执orderId=`"9007199254740993"`。重试同P、换traceId→当前授权通过后返回同首次业务回执，HTTP幂等成功200，业务写次数仍1；更新页面状态走查询。把serviceId改`"2"`→409 IDEMPOTENCY_KEY_CONFLICT、无新业务。此处为ORD013参数差异投影，未声称有真实order.create实现。

## E04 两会话并发屏障（W2-IDEM-003/004/005）

| 时序 | A | B | 预期持久事实 |
|---|---|---|---|
| t0 | Admission绑定S/P并commit | 等待同key绑定 | 1条RESERVED，0业务 |
| t1 | 锁记录，业务写未commit | 同参取锁被阻塞 | B不能写第二事实 |
| t2a | 成功事实+回执commit | 获锁/当前读看到SUCCEEDED | B重放；总业务1 |
| t2b（替代分支） | 回滚执行事务 | 获锁看到RESERVED | 原绑定留存，B同参可重新验证执行 |
| t2c（替代分支） | 执行未结束 | 等待预算2秒耗尽 | B为409 COMMON_CONFLICT/data:null；原R稍后重试 |

若B异参，Admission已可见时即KEY_CONFLICT；A最终回滚也不能让B覆写绑定。若两Admission同时首次插入，存储唯一性只允许一条，失败者重新读胜者。不能先内存查不存在就各写业务。

## E05 跨主体/跨命令/业务约束（W2-IDEM-004）

USER101/R与USER102/R操作各自合法资源可分别绑定；同主体不同commandNamespace也隔离。102访问101资源仍按权限拒绝，不返回101回执。商家员工原店scope与新店scope不同，客户端伪造staffId不能决定可信scope。管理员超级权限不跳过业务资格或脱敏。

**兼容反例**：即使公共表有两个作用域记录，SQL06 refund_application全局request_id唯一仍使第二主体失败，所以该模块接入前必须批准并完成旧约束映射。不能把仅公共记录可插入宣称跨主体集成通过。

**不同key反例**：同订单用R1/R2并发“当前未履约售后退款”与核销，公共幂等不消除两命令；业务guard/唯一/CAS保护裁决边界。核销先成功则旧未履约售后失效，不能再基于它退款；退款单先创建则禁止后续核销。不能泛化所有退款来源都只能一个成功：T05 §8允许服务开始后商家同意/24h路径在申请后发生核销，核销本身不自动否决该退款；新的核销后售后也按原资格处理。

## E06 崩溃与事务（W2-IDEM-005）

| 故障注入点（未来实测） | 推荐恢复，不变量 |
|---|---|
| Admission commit前 | 0绑定/0业务；新连接查原key再受理，不凭超时推断是否已提交 |
| Admission commit后、执行前崩溃 | RESERVED留存，0业务；同参获锁后可执行，异参冲突 |
| 执行写业务后、写回执前崩溃 | 本地业务/必要意图整笔回滚，Admission绑定仍在 |
| 回执序列化失败/commit前断开 | 业务和回执不得部分提交；新连接检查权威DB事实 |
| commit成功、HTTP返回前崩溃 | SUCCEEDED+业务都在，重试只返回已持久成功 |
| commit ACK未知 | 主库新事务查原key；成功重放、仍RESERVED且获锁才再执行；DB不可用503 |
| deadlock/锁等待超时 | 整笔执行回滚，有限次同S/P重试，不能新UUID或提交局部业务 |
| Redis清空/进程重启 | DB绑定/结果仍有效，不出现第二次业务写 |
| 外层事务尚未commit就发成功 | 禁止；这是原子性反例，不能用内层成功标记代替最终commit |

## E07 Provider/任务/事件故障边界

对于原Contract允许受理回执的命令：本地受理refundNo持久成功→Provider已收到但网络timeout→保持原业务号UNKNOWN/PROCESSING并查单。只有原渠道明确支持同号重放时才原单重提；公共组件不保证Provider恰一次、不新增refund_order。未知状态不是500或自动失败。反例：createPayment需要wechatPayParameters，不能用通用“已受理”冒充原成功，也不能重放过期支付参数；该命令完整分阶段映射待原Owner审查，本次不接入。

Task `TASK:ORDER_AUTO_CONFIRM:9007199254740993:0`重试attempt 1→2 requestId不变；合法新generation 1才另key。SYSTEM主体固定逻辑任务域，不随worker1→worker2变化。Event e1消费者A/B分别幂等；A已成功B失败，重放只让B再执行，消费成功标记与它的业务同commit。

## E08 失效/保留边界（W2-IDEM-005）

建议无自动TTL，因此绑定后1毫秒、24小时、7天及归档前后都仍是旧key，不能变成新执行。以模拟载荷清理时点T检查T-1ms/T/T+1ms：去重事实保持；合法兼容回执可重放，否则拒绝读取/设施不可用，不重新执行业务。未批准清理策略时没有清理动作；临时“缓存过期”不允许删除DB事实。

## E09 当前权限、版本与三端旧响应

同S/P成功后撤销动作权限→重放403（会话失效401），不返回敏感旧data/URL/actions；权限查询失败关闭。重新获权后当前权限全部通过，可返回旧成功事实，不以订单已变化/额度已用尽重新执行业务资格判定。旧resultVersion仍解码；无法兼容503并告警，不新建key重做。

C端退出/换用户，M端切店/撤权，Admin数据范围变更：本地保存的原意图只属于原上下文，取消自动重试/旧响应展示。Admin缺省参数每次生成UUID不是重试机制；人工重试须显式保留R和原参数。未确认旧请求结果前不能通过新UUID自动重复提交。

## E10 公共发号/时间提供器未来验收（W2-IDEM-001）

同worker同毫秒生成4096个互异ID；第4097次等待下一毫秒或有界失败，不能溢出。并发进程抢同worker只能一个有效持有；进程重启/时钟回拨不得复用历史ID，未具备持久高水位方案不能报PASS。不同worker无重复，epoch前/相对时间超41位失败。

Clock固定于业务截止前1ms/等于截止/后1ms，按原业务Contract比较；DB lease测试必须控制/读取真实数据库时间，不能仅Mock应用Clock声称真实租约通过。以上均未执行，实际ID提供器、MySQL库及Worker尚未交付。
