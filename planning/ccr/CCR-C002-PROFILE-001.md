# 编辑资料页缺口：性别、签名与保存依赖

状态：USER_ACCEPTED_WITH_CORRECTION / PENDING_CONTRACT_SYNC。2026-09-15；提出方/唯一 Writer：C-End，本次 C-002 主任务。用户在本提案确认问题中修正“性别没有保密只有男女；手机号真实入库，展示中间4位脱敏”，按此替换建议中的保密选项与历史默认；签名60字、昵称20字、四项同次保存和手机号只读按确认上下文保留。未同步权威API/Schema，未自批后端实现。

## 一页结论

最终 C 端 PRD §5.1.20 明确头像、名称、性别、个性签名可修改，手机号不可修改。Figma `127:1652` 也有这四项。已批准 HTTP10 §3.2.1 只有昵称和头像的读写，user_account 尚无用户性别/签名列；直接实现整页真实保存会出现用户以为保存了、实际没有保存的问题。

## 建议补充（待人工/Contract Owner批准）

1. GET/PUT `/api/v1/c/profile` 增加 `gender`：可设置值仅 `MALE / FEMALE`，页面文案“男/女”。已有用户在尚未填写时以空值表示缺少资料，不当成第三种性别；不擅自给存量用户分配男/女。用户选择后持久化对应值，不从微信/头像推断，不改变已有权限。原稿“保密”选项按用户明确裁决删除。
2. 增加 `signature`：允许空字符串，最多60个Unicode码点（按原稿60提示），服务端同规则校验；PUT省略表示不改，空字符串表示清空；不得将emoji代理对计为两字。字段计数示例：原稿“爱宠物的铲屎官一枚～”实际10字。
3. 一次保存对昵称、头像、性别、签名原子提交，沿用会话主体、`X-Request-Id`、冻结用户拒写和公共错误包裹；手机号与userId不允许写入。不引入新的产品能力。

4. 手机号数据库保存完整原始号码，不保存掩码号码替代真实号码；资料展示响应与本页仅拿 `phoneMasked`，11位号码显示前三位与后四位，中间四位替换为 `****`。当前user_account.phone与已批phoneMasked契约本来就是分开的，本次不把真实号码下发给不需要的页面。

影响：user_account新增gender与signature物理列、HTTP10字段补齐、内部资料DTO/命令补齐，以及相应真实MySQL/幂等/越权测试。只在批准后由明确Backend Owner同步；本前端分支不越权写DDL/生产迁移。

## 其他已发现差异与依赖

- PRD用户基础信息字段表昵称上限20字，而已批HTTP契约上限64。建议本页面按PRD限制20，服务端64保持已有兼容；是否统一契约由Owner在同步时明确，不能直接把64当产品输入要求。
- 头像选择/上传原稿明确可编辑，但当前没有可用的C端登录会话、资料HTTP实现或获批上传返回契约；仅PetService已实现。前端不能凭URL样例或fixture宣称上传落库成功。
- 当前app的WorkspaceProvider注入工程fixture，并不是已登录用户。真实页面必须待会话接入，不能直接用fixture.userId作为授权主体。
- 本次可以完成原稿视觉/本地状态交互测试。纯视图预览使用明确的测试入口，本地变更仅用于演示且提示“预览数据已更新”；不是业务Mock契约获批或真实保存。正式入口在依赖未具备时拒绝假保存。
