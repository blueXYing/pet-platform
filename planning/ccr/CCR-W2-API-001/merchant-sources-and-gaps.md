## 具体差异与解除条件

| ID | 差异 | 建议处理和限制 |
|---|---|---|
| MER-D1 | 25号补充明确将“协议版本管理与换版后是否重新同意”留待MER契约确认 | 本提案建议不可变版本、已签继续有效；待用户批准，绝不静默强制重签 |
| MER-D2 | SSOT §15：“存量订单继续履约”“存量退款/售后继续处理”；§26：“冻结/下线仅可查看”；25号D3重复后一句 | 建议明确新经营只读、保留§15存量例外；这是一处同层级规则冲突，需要产品确认后同步，不能仅以日期或旧API推定结论 |
| MER-D3 | merchant_staff没有user_id；主账号核销所需operator_staff_id没有真实映射 | 档案/成员关系分离，普通owner命令USER；绑定流程/核销操作者映射由AUTH/MER契约后续冻结；不造staffId |
| MER-D4 | staff停用时要检查/转派未完成订单，但order-api无已批完整在途指派守卫 | 员工停用/离职/软删除暂不实现；后续在订单Owner冻结检查与新指派互斥后推进，不以空实现解除 |
| MER-D5 | Schema没有入驻申请及审核/签约事实，ACTIVE不足以证明四态 | 提出最小资格投影和电子同意存储；完整申请材料/主体去重/OCR同步后才可真实装配；无事实返回503 |
| MER-D6 | HTTP/内部准入历史文本仍写外部签约Provider、失败回调 | 后续权威同步按已批§26删除该技术依赖；保留展示枚举，不生产SIGNING/FAILED假场景；OD-W0-002保持RESOLVED |
| MER-D7 | 岗位、资质、staff软删除、营业资料字段及页面CRUD未完整入Schema | 保留在MER/M/ADM原Scope，不把基础DTO当作所有页面字段交付 |

MER-D3/D4/D5/D7主要是技术依赖，由开发侧继续形成契约，不要求用户逐字段设计数据库。MER-D1/D2才是本轮需产品确认的两个具体语义。B-FROZEN-WRITE是既有未决，不在本提案偷偷关闭。资金OD-W0-001不因电子协议解除。
