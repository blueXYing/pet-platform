## 已批准的业务方向

| 讨论项 | 对应决定 | 结论 |
|---|---|---|
| 1 可用人员 | SCH2-D1 | 在职、在岗、归属门店、具备目标服务能力，且 AVAILABLE 排班区间并集无空档地覆盖整个查询时段，才计入。确定没有排班/能力=0 人；读取失败不是 0 人。 |
| 2 能力粒度 | SCH2-D3 / SCHW-D7 | 按具体服务项授权，页面按类目分组；新增同类目服务不自动赋权。该裁决覆盖 PRD 中将“可服务类目”直接视为整个类目授权的解释。 |
| 3 双时段 | SCHW-D2 | 上门 PICKUP、送回 RETURN 分开维护，到店 GENERAL；分钟级。页面提示/限制无效组合，预约服务端最终强校验 returnStart >= pickupStart + 120 分钟；本次开窗命令不检查全部组合，不免除最终校验。 |
| 4 重叠与删除 | SCHW-D3 | 同店、同服务、同类型 OPEN 窗口不重叠；同员工 AVAILABLE 排班不重叠；相邻半开区间允许。关闭/重开替代物理删除，保留历史。 |
| 5 已占用时段 | SCHW-D4 | TEMP_LOCKED/CONFIRMED 占用期间禁止关闭、降容量、改时间；升容量可放行。种类或服务目标变更不能绕过保护，精确守卫与预约锁协议需在实现前冻结。 |
| 6 临时停业 | SCHW-D5 | 允许部分关闭。有占用的保留并列入 blockedWindows；其余进入 closedWindows。界面明确“部分关闭、仍有未关闭时段”，全部受阻时不显示关闭成功。跨天部分相交整窗处理、逐窗恢复，本轮没有持续性的停业开关或批量恢复。 |
| 7 人员变更保护 | SCHW-D6 / D7 | 不接受 v0.1 “排班关闭无占用守卫”及无保护地撤销能力。先明确已占用容量、已指派订单保护与并发锁协议，相关减少可用性的写入在事实/契约缺失时不得放行。**本次没有批准具体保护算法或新占用事实接口。** |
| 8 分工与顺序 | SCHW-D1 / D8 | SCH-004 负责窗口/排班/能力；员工档案由 MER 原模块实现，M-002 承接页面；运营只读监管延后至 SCH-003 具备占用事实后交付，不取消。 |
| 9 原因与审计 | SCHW-D9 | 关闭、临时停业以及减少人员可用性的操作必须填写原因。全量状态变更记录操作人、时间和动作；本轮不能把原因仅设为空列却不接收/保存。 |
| 并发能力编辑 | SCHW-D7 | 不接受静默 last-write-wins；过期编辑产生冲突提示，用户重读后决定，不自动覆盖。具体集合版本/CAS 存储方案需要契约同步。 |

## 技术方向及批准边界

- SCH2-D2/D4～D7 沿用建议：独立的门店员工明细内部 API，模块经 API 协作；故障失败关闭；真实提供器、默认关、测试与契约同步。接口状态标签可用 IMPLEMENTED_DEFAULT_OFF，但只能在实现与测试实际通过后更新，当前不能提前标 IMPLEMENTED。
- SCHW-D9/D10 沿用独立审计与两类错误码方向；幂等、权限、版本冲突与模块边界不变。
- “每人最多 200 项服务”在上一轮说明中是**待确认限制**，不是建议定稿。该数值不纳入本回执；不得以服务项数量护栏为名直接引入业务上限。
- 此次 scope 是服务发布收尾及草案审阅。排期业务代码、Schema 迁移和生产开关不在本轮实施。
