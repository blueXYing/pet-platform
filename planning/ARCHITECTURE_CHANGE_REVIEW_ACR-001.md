## 1. 评审结论

建议保留后端和交易契约，前端采用“一个 Taro + React + TypeScript 微信小程序，一个 React + TypeScript + Vite 运营网页”。用户和商家是同一小程序中的两个业务工作区，不生成两个独立小程序，不新增用户端网页。App 后续单独评审，不提前选择 React Native 或承诺页面代码无需修改即可复用。

前端三个目录目前均只有 README，无 package.json 或页面实现，因此 Vue 改 React 的现有代码返工成本低。主要成本是小程序工程组织、登录与身份上下文、平台能力适配、原始素材还原和真实小程序测试。两个工作区共用同一登录并切换身份，已见商家最终 PRD §5.2；不是新增产品能力。

本评审不修改业务规则，也不把原型包含的全部 App/未来页面纳入 V1。尚未改技术基线、既有 Issue、Allowed Modules、Schema/API/Event 或代码。

## 4. 建议方案与备选

### R1 小程序技术方案：建议 Taro + React + TypeScript

Taro支持React，并提供遵循小程序的页面、路由和平台API规范；它不是把ReactDOM网页直接放入微信。官方说明见 [Taro React概述](https://docs.taro.zone/docs/3.x/react-overall/)、[当前目录结构](https://docs.taro.zone/docs/folder) 和 [平台API](https://docs.taro.zone/docs/apis/)。

建议：单一小程序应用、一个AppID，用户和商家逻辑目录分开；商家工作区按普通分包加载；小程序使用Taro平台路由和请求适配。共享登录、错误处理、类型和设计变量，不共享浏览器专用UI组件。具体Taro/React/Node版本须在批准后的骨架验证中形成兼容锁定组合，不直接写latest。

备选：原生微信小程序可最大限度直接使用原生能力，但不能满足“全部前端采用React”的统一方向，需人工另行调整方向；本次不默认采用。React Native解决后续App而非当前小程序，不作为本次替代。暂不引入第二套小程序框架。

风险：第三方React网页库不一定适配小程序；分包与图片会影响包体；身份切换存在上下文隔离要求。应以授权后的真实小程序构建和实机结果验证，不能以Web预览通过代替。

### R2 运营网页：建议 React + TypeScript + Vite

运营端是独立网页应用，继续调用现有Java后端。React官方提供Vite+React+TypeScript路径，但路由与数据获取仍需自行组合，见 [React构建指南](https://react.dev/learn/build-a-react-app-from-scratch)。建议使用React Router处理Web路由，保留独立请求适配；本次不引入SSR/Next.js或额外Node业务服务。业务状态和鉴权仍由Java后端负责。

备选：React全栈框架可在将来有SSR等明确需求时评估；现有运营应用没有此项交付要求。状态管理先使用React局部状态与受控上下文；若共享状态复杂再单独评估库，不机械以另一大库替换Pinia。UI组件库不得作为还原原型的限制条件。

### R3 工程组织：建议一个小程序工程，分业务所有权

以下只为待批准目录示意，当前未创建或移动任何目录：

```text
backend/                         现有后端
frontend-miniapp/                一个Taro应用、一个构建与发布入口
  src/consumer/                  用户功能，C-End负责
  src/merchant/                  商家功能，Merchant负责
  src/shared/                    共享登录、请求、UI基础和素材索引
frontend-admin/                  React运营网页
e2e/                             Web、小程序及跨端测试
```

旧frontend-c与frontend-merchant如何迁移由确认后的任务同步处理，不保留两个竞争的小程序应用壳。不创建用户Web或App工程。

共用package.json、锁文件、app配置、共享登录及公共素材目录指定唯一编辑者。建议C-001承担统一小程序壳，M-001只建立商家工作区并使用该壳；C-End与Merchant在明确共享接口/固定基线后继续并行。公共能力修改由所属Issue登记Owner并评审，不开一个长生命周期全项目Thread。

Backend Core、Transaction Backend、C-End、Merchant、Admin、QA六岗位继续存在；各自只领取依赖已满足的短Issue。评审期间全部停止派发，本次不启动任何代理或开发任务。

### R4 身份切换与平台适配：保持产品规则，补齐技术契约

商家PRD §5.2已经要求：默认宠物主，个人中心进入商家工作台，校验最新权限；切换不退出登录；未通过审核/签约不得正常开通；被冻结时保留规定的历史/售后处理能力。因此不能简单用前端isMerchant布尔值代替鉴权，也不能因商家被下线就删除存量履约入口。

保持/api/v1/c、/merchant、/admin分区不变。建议请求上下文、缓存键明确区分用户、商家、门店与当前工作区，切换或权限撤销时清除/重取相应数据；切换前发出的请求返回后不能写入另一身份的界面。深链直达商家页面也须鉴权。小程序登录、支付、扫码、上传通过平台适配层，Web请求实现不直接复用于小程序。

**CCR-ACR-001（本评审内草案，未批准）**：关联AUTH-001、C-001、M-001及后续接入任务；明确会话/可用身份/门店权限响应、工作台准入、切换是否需要服务端命令、权限变更后的缓存与失效协议、Mock结构及403/登录失效处理。依据商家PRD §5.2、HTTP登录与RBAC语义；不新增业务行为。API影响确定需要细化，Schema/Event是否变化待评审，不预设新增接口路径或表。测试覆盖身份切换、越权直达、权限撤销、缓存串用和在途请求串写。确认后由Contract Owner按CCR处理，前端不得编造公共DTO。

OD-W0-002签约接入与OD-W0-003运营权限矩阵仍未决，本ACR不代替它们；原有三个技术CCR继续保留。

## 5. Figma原稿一比一还原：落实方式与验收

### 已掌握的设计证据

设计文件：[宠物小程序](https://www.figma.com/design/bp2vpcjjA5vZbHvtKkA8wl/?node-id=0-1)。本会话已通过只读API取得文件结构，记录版本2397539525915641008、更新时间2026-09-10T09:50:47Z；1个顶层Page、115个顶层FRAME，其中112个宽402，另含图标FRAME。**这些不是115个已确认V1页面**，有重复、状态变体、素材和未来功能。这里只确认读取的结构，不声称已逐帧视觉精审或完成切图导出。

用户已说明这是App与小程序共用原型，因此积分商城、支付密码、聊天等图稿留在原设计中不构成重新开启V1功能的理由。商家设计待提供，不从用户端设计猜商家页面。原型后续改变时按版本记录差异，不悄悄替换验收基准。

### 不可降级的还原要求（用户已明确）

1. 对获准V1页面使用Figma原始图片、图标、插画、背景切图；不以图库、AI图片、近似图标或Emoji替换。纯布局、边框、圆角、文字等采用真实组件/样式精确实现，不把整页切图铺成假界面。
2. 原稿为视觉实现基准：位置、尺寸、间距、颜色、字体/字重/行高、图片裁剪、圆角、阴影、层级及交互状态逐项对齐。业务规则仍服从SSOT，不能因原稿含未来功能而实现。
3. 范围外功能及入口不进入V1。删减会改变布局的页面先给出原稿节点、删减项与调整后的布局供人工确认；不自行重排，也不直接将未来页面套为当前页面。
4. 缺失切图、字体或组件状态先列缺口，不擅自找近似替代。需要转换素材格式时必须从原始素材转换，保留视觉一致性并记录转换关系。
5. 原生胶囊、系统状态栏、微信支付/授权界面、系统字体渲染等不可控差异单列确认，不承诺由应用控制系统像素，也不以此放宽可控页面的还原要求。

### R5 建议的可验证交付方式

- 建立逐页清单：Figma文件版本、Frame/节点ID、V1范围、路由、状态变体、原始切图、验收截图、差异记录及确认结果。采用节点ID消除同名页面歧义。
- 建立素材清单：节点ID、原图/导出切图、格式、倍率、尺寸、哈希、引用页面；选用原生图像资源或Figma导出。透明图按需PNG，照片使用原资源；矢量是否转栅格以小程序能力和像素比验证，不提前盲目压缩。原始文件保留，发布派生文件单独对应。
- 固定获准Frame的设计尺寸、微信版本/基础库、设备窗口、像素比、测试数据、滚动位置、时间与动画状态，逐页生成真实小程序截图，与Figma导出图做叠图/差异图。402是已观察设计宽度，不等于所有手机固定402px；标注的长图也不等于设备视口高度。
- 对同一基准尺寸逐项消除可控偏差；其他窗口尺寸检验排版、安全区域、图片清晰度与交互。字体抗锯齿等差异必须记录原因；不以总体相似度高掩盖局部错位。
- 验收条件建议为“全部已批准V1页面与状态有对照证据，无未处理或未经确认的视觉差异，交互可用”。首个代表页面由人工确认后固化测量方法；不擅自将95%相似视为完成。
- 素材分包、按需加载及运行时图片资源方案需结合实际包体评估；不把所有原图塞进主包。不会把Figma短期导出链接直接作为产品图片服务。

Figma令牌只用于读取，未写入本稿、仓库配置或素材清单。后续素材导出不等于获得全部图稿的产品范围批准。本轮仅编写评审，未批量导出素材或制作页面。
