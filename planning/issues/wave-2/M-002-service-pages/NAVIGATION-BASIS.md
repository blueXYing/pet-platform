# M-002 服务管理页 — 商家工作区导航依据（NAVIGATION-BASIS）

日期：2026-09-22。角色：C（前端，本轮同时承接 M-002 页面实现）。
目的：按用户 2026-09-22 裁决第 4 点，核对商家端 PRD、技术基线与既有裁决，给出服务管理页导航挂接的**证据链结论**；本文档不改变任何产品规则。

## 1. 结论（先行）

1. **V1 商家端没有 TabBar**。商家 PRD 全文无导航/页面结构章节（§4 是"整体业务流程"），未定义任何底部 Tab；与 C 端 PRD 明文"首页、社区、消息、我的四个底部 Tab"（02-PRD-C端 §4，:132）形成对照。设计稿 10:5255/11:5768 底部的 首页/订单/核销(中央)/消息/我的 五 Tab（frame-summaries 153:4581–4590/153:1281–1290）**无任何已批准依据**，与 C 端 PRD 四 Tab 约定及已交付工程壳共享导航（首页/服务/宠友圈/消息/我的）均不一致，属草稿导航（本工作第一阶段 INVENTORY §3 D1 / §4 差异6 已登记）。
2. **既有批准的商家导航路径 = 个人中心 → 商家工作台（MS-3 页）→ 工作台功能入口 → 各功能页 → 返回工作台**。服务管理页按此挂接：从工作台 ALLOWED 态新增"服务管理"入口进入，页面返回键 navigateBack 回工作台；工作台"返回"回 consumer 壳（既有实现）。
3. **准入门槛沿用既有裁决**：服务管理入口仅在 admission=ALLOWED 态展示；LIMITED（下线/冻结）态不提供新经营入口（SSOT :1143"下线停止新订单/新预约"，服务写入属新经营业务）；DENIED/未登录不可达。页面自身仍做坐标/准入校验（防深链绕过），失败关闭并引导去工作台。
4. **不做全局导航变更**：不新增 TabBar、不改 app.config.ts 主包页面与共享导航组件；仅按既有先例在 merchant 分包注册新页面 + 在工作台页（M-002 自己的文件域）加一个入口按钮。
5. **缺口登记（不阻塞）**：商家端"工作台内各功能页之间的导航层级"（如工作台是否用统一二级导航头）PRD 未细化；本切片沿用 MS-3 工作台页的"返回按钮+标题"头部语言（该页无原稿、按申请页语言实施的既有先例）。设计稿头部为"返回箭头+标题"（10:5301 商品管理 16px/700 #3c3c3c + 左侧返回箭头切图），与服务管理页设计一致，直接采用设计稿头部；工作台页自身维持既有实现不动。

## 3. 服务管理页挂接方案（依上述结论实施）

```text
consumer 个人中心/壳（既有，不动）
  └─ /merchant/pages/workspace/index（MS-3 工作台，既有；本切片仅在 allowed 态卡片加"服务管理"入口按钮）
       └─ /merchant/pages/services/index   服务管理列表（新增，merchant 分包）
            ├─ 返回 → navigateBack 回工作台（栈空时 redirectTo 工作台）
            ├─ 卡片点击 → /merchant/pages/services/edit?serviceId=…（编辑/详情，ACTIVE/REVIEWING 只读态）
            └─ "添加服务" → /merchant/pages/services/edit（新增）
       └─ 编辑页返回 → navigateBack 回列表
深链/消息中心跳转：服务管理页自身校验 merchant 工作区坐标与准入（E5"深链也须验证"），不满足=失败关闭+引导去工作台
```

- 路由注册：`app.config.ts` merchant 分包 pages 追加 `pages/services/index`、`pages/services/edit`（既有分包行内追加，不动主包 pages，符合 C-End 对全局配置的唯一 Writer 先例——本轮由角色C本人执行）。
- 消息中心（既有页面）兼容服务审核结果通知跳转：`routeForNotification` 白名单机制可扩展（消息体不携带 URL，目标页自校验），新增 SERVICE_REVIEWED/SERVICE 类型 → 服务管理列表页；商家收件箱与通知下发本身归角色E，前端不冒充已完成。
- 工作台入口按钮不新增文案外的导航语义；LIMITED/DENIED 态不加"服务管理"入口（E4）。
