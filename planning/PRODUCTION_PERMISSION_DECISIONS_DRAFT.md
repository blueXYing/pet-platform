## 已确定，不重复裁决

1. 运营不能正常代接单；异常关闭属于高权限、二次确认、完整审计操作，其既有契约为异常关闭并全额退款。
2. 部分退款只能来自运营售后裁决；售后首次正式裁决即终局，不增加用户或商家的二次复审。退款创建与核销互斥规则不变。
3. SSOT 允许运营立即下线商家，停止新订单但保留存量履约、退款和售后。
4. PRD 已要求：提交人不得复核本人提交的内容；双人复核中的执行人与复核人必须是不同账号；权限变更需要双人复核。
5. RBAC 加全部/城市/商家数据范围，查询与导出均需校验；敏感数据按既有规则脱敏，审计不可篡改/删除。超级管理员也没有绕过业务硬规则的依据。

术语：二次确认是同一人确认操作；双人复核是两个人审核；售后二次复审是正式终局之后再审案件。三者不能互换。若采用裁决前双人复核，只能在首次正式裁决生效之前完成，不能先产生退款再等批准。

## 待裁决问题

### P1 角色名称是否统一为六个角色

现状：§4.1有三行同名“运营人员”，分别承担编辑、经营治理、准入审核；两行同名“财务只读”，分别承担财务和审计。§4.2却使用运营编辑、审核员、运营管理员、财务只读、审计只读，并把超管权限塞进运营管理员列。

- A（建议）：按职责统一为运营编辑、审核员、运营管理员、财务只读、审计只读、平台超级管理员。超管有独立权限列；具体权限按动作分配。
- B：保留较少角色，用单独授权区分这些职责；必须明确各账号动作权限，不能以“运营人员”名称默认全开。

建议理由：A与现有矩阵最接近，主要消除名称错误，不新增业务岗位能力。六角色不要求现在招聘六人，但要求双人复核的环节不能由同一个人自审。

### P2 “财务只读”能否执行资金相关操作

现状：§4.1写“提现审核与打款（如被授予执行权）”；§4.2给退款重推、补偿、对账差异处理、提现打款标●；§10.4又要求资金接口运营只读，并禁止修改渠道金额、手工标记到账和代商家提现。

- A（建议）：财务只读严格只读；查看及获准导出相关台账，不拥有退款执行、补偿、打款权限。资金执行岗位及动作等待 OD-W0-001 的资金基线确认，本次不擅自删除未来需求。
- B：明确拆出独立“财务执行”角色；须一并确认资金系统与本后台的执行边界、允许动作和审批流程，不能仅改名后把现有●全部授予。

已经批准的业务退款、售后退款可由系统按既有契约执行；“财务只读无执行权”不阻断系统自动退款。真实退款查询/重试与人工改金额是不同权限，不能合并为一个“资金操作”。

### P3 谁能提交首次正式售后裁决、谁能处理交易异常

现状：§4.2给审核员“售后与投诉裁决”●、运营管理员▲；§4.1又称运营管理员负责售后裁决、高风险双人复核。HTTP定义了运营身份和RBAC，却未给具体角色映射及裁决前审批协议。

- A（建议）：审核员中获授售后权限者处理案件、拟定结论；涉及全额/部分退款的结论由另一名获授复核权的运营管理员在生效前复核。非退款结论由获授售后权限者按既有流程正式裁决。交易异常关闭、退款技术重试单独授权运营管理员，不授予普通编辑或只读角色。
- B：获授售后权限的审核员可直接做首次正式裁决；明确哪些动作属于既有“高风险双人复核”要求，并另定范围，不能把整个双人复核要求取消。

A的优点是减少金额裁决误操作，代价是需要两人在线处理和补齐裁决前复核契约；B处理更快，但必须把高风险范围写清。任何方案都不引入售后二次复审，不允许旧未履约售后在核销失效后继续退款。

### P4 双人复核覆盖哪些动作，紧急商家下线如何处理

现状：§4.2的▲包括商家下线、渠道授权、券与积分配置、账号处置、系统参数等，但未逐项定义发起者/复核者/生效时点；HTTP异常关闭仅明确“二次确认”。权限变更双人复核已经确定。SSOT允许商家立即下线。

- A（建议）：既有▲动作在生效前由不同账号复核；权限分配由超管发起、另一名有权限复核职责的超管复核。商家紧急下线设为获授权运营管理员立即执行、填写原因并审计，另一人事后复核；事后复核不自动恢复商家或取消已产生事实。需要产品明确此下线例外。异常关闭与退款重推是否纳入双人复核随本项明确，建议纳入，不仅依靠确认弹窗。
- B：逐项列出不同审批等级与复核角色，保持已经明确的双人复核约束，并保证SSOT的立即下线能力。未列明动作不能由研发自行选审批等级。

不建议本轮凭空引入金额阈值、复杂多级审批或修改30分钟/24小时等业务时限。系统参数权限不意味着可修改封板产品规则。首次超管初始化属于受控工程初始化，不能被做成生产权限变更的通用免审入口。

### P5 运营编辑的“可操作”是否包含直接发布

现状：§4.1说编辑无审核权、提交后进入审核队列；§4.2却对“消息与公告发布”“百科与品种库维护”标●，而审核员的消息公告列为—。矩阵未区分草稿提交与正式发布。

- A（建议）：拆成编辑/提交、审核、正式生效三种动作。运营编辑编辑并提交，另一名获授内容审核权限者审核，系统按批准结果发布；需补齐审核员对公告等内容的审核权限。同一人不得审核自己提交的内容。系统自动产生的订单等业务通知不进入人工内容审批。
- B：逐项指定允许编辑直发的低风险内容，其他仍审核；这属于对§4.1通用约束的明确例外，必须逐项确认，不可直接把所有●解释为发布权。

### P6 超管是否自动获得全业务操作与全部数据访问权

现状：§4.1把超管定位为系统与权限根；§4.2没有独立超管列，只在账号/角色/权限管理标“●（超管）”。系统设置要求账号绑定角色与数据范围，但没有明确超管的业务权限继承。

- A（建议）：超管默认负责账号/角色/权限管理，不自动拥有退款裁决、资金执行和敏感数据明文权；需要兼任业务职责时显式授予对应权限与数据范围，仍受双人复核及禁止自审约束。普通账号按职责授予城市/商家范围，全平台数据范围明确授权。
- B：超管默认拥有V1已批准的全部业务动作及全平台数据范围；仍不得绕过脱敏审批、双人复核、审计或SSOT硬规则。需接受其业务误操作影响范围更大。

本项不改变PRD已有的全部/城市/商家范围类型；多角色合并、冲突权限计算等技术行为在产品选择后由AUTH契约明确，不由前端Mock定义。

## 建议角色职责摘要（仅在对应A选项获批后生效）

| 角色 | 职责 | 不自动获得的权限 |
|---|---|---|
| 运营编辑 | 内容/基础资料草稿与提交 | 审核本人内容、资金执行、账号授权 |
| 审核员 | 获授范围内的准入/内容审核、售后处理 | 审核本人提交、资金系统执行；退款裁决按P3待复核 |
| 运营管理员 | 经营治理、获授的交易异常处置与复核 | 修改渠道金额、普通代接单、绕过双人复核 |
| 财务只读 | 获授范围内的资金台账查询/导出 | 退款重推、补偿、提现打款 |
| 审计只读 | 审计和留痕查询/获准导出 | 修改或删除业务数据、篡改审计 |
| 平台超级管理员 | 账号与权限管理 | 自动继承全业务写权限或敏感明文权 |

只读仍可拥有受控导出权限；导出不是修改业务事实，但仍需既有用途、脱敏、水印和数据范围控制。功能权限、数据范围、敏感字段权限分别校验。
