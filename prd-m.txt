3. 需求概述
业务背景：原始 C 端需求已覆盖用户预约、内容社区、支付、售后与商家入驻等能力，但商家侧缺少独立的工作台定义。门店在接单、排期、核销、售后和经营统计无统计页面及维护工具，效率和可追踪性不足。
需求目标：为商家提供一个以“数据看板 + 高频功能入口”为主的工作台首页，快速呈现待办与经营状态，并承接订单、排期、服务、店铺、员工、核销、售后、评价、客户和数据等核心操作，形成与 C 端用户动作一一对应的履约闭环。
适用范围：覆盖商家登录与身份切换、入驻审核开通、首页数据看板、订单管理、排期管理、服务项目管理、员工与服务人员管理、店铺资料、平台订单核销、第三方团购核销、售后管理、评价管理、客户档案、消息中心和经营数据中心。
配套关系：本说明书为《C端宠物主用户1.0需求规格说明书》的商家侧承接文档。凡 C 端用户产生的下单、支付、改期、退款、到店核销、评价、售后动作，均须在本说明书中找到对应的商家侧承接点与状态流转定义。产品原则：首页不堆复杂图表，不做长信息流；优先展示今日待办和关键经营数字；所有高风险动作必须带状态校验、原因记录和操作留痕；已支付订单和已生成快照的数据不得被后续编辑覆盖。
配置原则：商家可自主维护服务内容、可预约时间和店铺基础资料；系统提供默认生成与人工调整并存的能力，默认配置可被商家按门店实际情况覆盖。
用户改期、退款、核销、评价回复四类动作
原型/截图说明：文档内保留的原型截图仅用于页面结构、交互位置与视觉参考；若截图中的旧文案、状态、编号、时限或流程与本最终版正文及 V1.0 SSOT 冲突，以本最终版正文及 V1.0 SSOT 为准。
4. 整体业务流程
商家登录与身份切换：同一微信账号默认以宠物主身份进入 C 端，商家入口只放在个人中心；已入驻用户在个人中心点击“商家工作台”，系统校验最新权限状态后进入商家端，宠物主与商家双身份互不冲突、可随时切回。
商家入驻：个人中心发起入驻申请，填写商家资料、资质和门店信息，支持草稿保存与断点续填。审核通过且签约完成后开通工作台。
工作台进入：审核通过后首次登录，系统默认打开首页数据看板，展示待办、营收与快捷入口。
日常接单：用户支付成功后订单进入“待确认”，商家在30分钟内完成接单或拒单；超时系统自动接单。接单后订单进入“待服务”。
排期履约：维护可预约时段、临时停业、服务时长和可预约容量，保证分钟级资源锁定和释放正确；上门接送型服务分别占用上门与送回预约时段，到店型服务按服务时长占用对应时间区间。
改期与退款承接：用户改期后同步更新预约与容量；预约开始前退款由系统直接处理，预约开始后退款进入商家24小时处理队列。
平台订单核销：用户到店出示动态核销码，商家扫码并二次确认后完成核销，订单由“待服务”流转为“已完成”，开放评价与售后入口。
第三方团购核销：顾客到店出示美团 / 大众点评券码，已授权员工扫码或手输券码完成核销，不计入平台订单与资金口径。
售后与评价：用户发起售后或提交评价后，商家在工单内提交说明与证据，对评价进行回复或对违规评价发起申诉，运营介入处理争议。
经营复盘：商家查看数据看板、评价、客户档案和经营数据，持续优化服务和排期。
5. 功能详细需求内容
本章为设计、研发和测试的核心依据。每个模块保留页面定位、用户角色、使用场景、核心功能、业务规则、交互方式、异常或边界情况，以及字段级设计表。
5.1 首页数据看板
页面定位：登录后默认展示的工作台首页，先让商家快速看清“今天要处理什么”和“店铺经营得怎么样”，再进入具体功能模块。
用户角色：商家管理员、门店店长、被授权员工（按角色控制可见指标范围）。
使用场景：商家每天开工后查看待办、接单情况、营业状态和经营概览，快速决定当天的处理优先级。
核心功能：
顶部展示店铺状态、营业时段、当前评分和未读消息。
中部展示今日订单、待确认、待服务、今日营收、本月营收、待处理退款、待处理售后等简易指标卡。
底部提供订单管理、服务管理、店铺资料、订单核销、团购核销、售后工单、评价管理、客户档案、数据中心和消息中心等入口。
指标卡支持点击直达对应功能页，并自动带入对应状态筛选条件。
业务规则：
各指标按单店维度统计，不与平台整体数据混淆。
数值正常为 0 时直接显示 0，接口异常或未取到数据时显示 --。
首页不放复杂 BI 图表和长列表，保证首屏可快速扫描。
店铺暂停营业、已冻结或已下线时必须显著提示当前状态，避免误以为仍可接单。
“待确认”指标统计距自动接单剩余不足30分钟的订单，并排在待办首位。
交互方式：
点击指标卡跳转对应功能页并带入筛选条件。
顶部店铺状态可一键切换营业中 / 休息中，切换需二次确认。
异常或边界：
没有待办时显示空状态，不隐藏首页模块。
接口失败或权限失效时，保留页面框架并提示重新登录或刷新。

5.2 登录与身份切换
页面定位：承接商家身份的进入、校验与退出，保证只有审核通过的账号可以使用商家工作台。
用户角色：已登录宠物主用户、入驻申请中的用户。
使用场景：已入驻商家从 C 端个人中心进入商家工作台；商家在宠物主身份与商家身份之间来回切换；账号被冻结或审核被驳回时进入工作台的拦截与提示。
核心功能：
宠物主身份用户在个人中心可见“成为商家”入口，提交入驻申请后入口变更为“入驻审核中”。
审核通过且签约完成后，入口自动变更为“商家工作台”，点击进入商家端。
商家端顶部提供“返回 C 端”入口，可随时切回宠物主身份，两种身份互不冲突。
每次进入工作台前系统校验最新权限状态，包括入驻审核状态、签约状态、门店冻结状态与子账号启用状态。
支持商家主账号为门店开通子账号，子账号登录只可见被授权范围内的功能。
业务规则：
未入驻、审核中、已驳回三种状态下不得进入商家工作台，点击入口时展示对应状态与下一步引导。
已通过但未完成支付服务商签约的账号，进入时提示先完成签约，并展示签约入口与失败原因。
登录态失效时保留当前页面上下文，重新授权后返回原页面。
交互方式：
进入工作台前展示轻量加载态，校验通过后直接进入首页数据看板。
身份切换不退出登录，仅切换工作台上下文。
异常或边界：
权限校验接口失败时不允许放行进入工作台，展示重试入口。
商家账号被冻结时，允许查看待处理售后与历史订单，保证用户侧争议不被搁置。
用户注销账号时，若名下存在未完成订单或售后工单，拦截注销并提示先处理完毕。

5.3 订单管理
页面定位：处理用户预约订单、支付订单、改期请求、退款请求和异常订单，是商家日常操作频次最高的页面，也是 C 端用户下单后唯一的商家侧承接入口。
用户角色：商家管理员。
使用场景：商家根据订单状态完成接单、拒单、改期承接、退款处理和服务完成，保障履约闭环。
核心功能：
支持全部、待支付、待确认、待服务、已完成、已取消、退款待确认、退款中、已退款、部分退款、售后等状态筛选。
支持按订单号、客户手机号、服务名称、服务人员和日期搜索。
可查看订单快照、服务内容、预约时间、上门与送回时段、服务地址、支付状态、客户信息和联系方式。
支持接单、拒单、完成服务、查看改期记录、查看退款记录和查看操作记录。
支持填写接单备注、拒单原因、完成说明和处理反馈，形成订单处理闭环。
业务规则：
订单状态统一为：待支付 / 待确认 / 待服务 / 已完成 / 已取消 / 退款待确认 / 退款中 / 已退款 / 部分退款 / 售后，状态流转见 6.1。
商家确认、拒绝和完成服务必须校验当前订单状态，重复操作不得造成重复退款或重复履约。
已支付订单中的服务名称、金额、排期快照和优惠信息不允许被后续改价或改期覆盖。
已取消、已关闭、已退款的订单仅允许查看，不允许继续操作。
支付回调延迟时订单先显示处理中状态，不得展示为支付失败。
订单列表与首页待办、排期日历、数据中心使用同一状态口径。
交互方式：
待确认订单高优展示，按剩余自动接单时间正序排列，支持快速接单或拒绝。
订单详情页展示完整快照、状态时间轴、改期记录、退款记录、操作记录和关键操作按钮。
订单详情页可直接查看用户授权范围内的档案。
异常或边界：
重复点击不得造成重复退款、重复完成或重复释放槽位。
订单所在服务已下架时，按原快照继续履约，并在订单详情显著提示服务已下架。
网络异常时按钮置灰并展示处理中，失败后提供重试，禁止重复提交。
5.3.1 订单接单与拒单
页面定位：处理用户支付成功后的待确认订单，是商家履约的第一道闸门。
业务规则：
用户支付成功后订单进入“待确认”，商家须在 30分钟内完成接单或拒单。
超过30分钟未处理，系统自动接单，并向商家推送结果通知。
商家仅在“待确认”阶段可拒单；拒单必须填写原因并选择原因分类，提交后系统自动发起原路退款，订单进入“退款中”。
订单一旦确认（含超时自动接单），商家端不再提供单方取消或拒单入口；用户预约开始前可直接退款，预约开始后退款进入退款待确认。
拒单原因需同步展示给 C 端用户。
异常或边界：
拒单与自动接单在同一时刻并发时，以先到达服务端的请求为准，后到请求返回当前状态并提示刷新。
拒单触发的退款失败时，订单保持“退款中”并进入运营异常任务，商家端展示“退款处理中”且不释放槽位。

5.3.2 用户改期承接
页面定位：承接 C 端用户发起的预约改期，保证商家侧订单时间、排期占用和待办提醒同步更新。
核心功能：
订单详情展示改期记录：原始预约时间、当前预约时间、改期次数、剩余可改期次数、每次改期的申请时间与处理结果。
改期成功后首页待办、订单列表和排期日历同步刷新，原槽位释放、新槽位置为已占用。
支持按“存在改期记录”筛选订单，便于商家核对履约时间。
业务规则：
C 端每笔订单默认允许 1 次改期，改期仅限同一商家、同一服务，不可更换服务或门店。
改期由系统先原子锁定新槽位，锁定成功后再释放原槽位；新槽位锁定失败则保留原预约不变。
改期提交后订单回到“待确认”状态，并重置30分钟商家确认倒计时；商家超时未处理则自动接单，订单按新预约时间继续生效。
改期后以新的预约开始时间作为退款前/后判断基准。
改期不涉及退款，原订单已支付金额与优惠权益快照保持不变，仅原子交换预约时段与占用记录；改期记录需完整留痕。
异常或边界：
并发改期或改期与商家接单并发时，以服务端版本号为准，冲突时提示“订单状态已变化，请刷新后重试”。

5.3.3 退款处理
页面定位：承接用户退款。预约开始前由系统直接处理；预约开始后进入“退款待确认”由商家处理。
核心功能：
提供退款记录列表，支持按退款状态、订单号、申请时间筛选。
退款详情展示退款预览：订单实付金额、优惠券返还说明、退款状态与预计到账时间。
退款成功后订单进入“已退款”，仅在渠道退款最终成功后释放正式占用；全额退款时，仍在有效期内的平台券恢复可用（剩余不足24小时则延长至退款成功后24小时），并全额扣回本单下单奖励积分。
退款失败或结果不明时，展示“退款处理中”。
业务规则：
预约开始前：用户申请退款后系统直接创建全额退款单，无需商家确认。
预约开始后：用户申请退款进入“退款待确认”；商家24小时内仅可同意全额退款或拒绝，超时系统自动全额退款。已核销订单拒绝后可进入售后。
退款以支付服务商回执为最终结果，使用唯一退款请求号防重，禁止重复退款。
全额退款成功后，仍在有效期内的平台券恢复可用，剩余不足24小时延长至退款成功后24小时；部分退款不返券。
仅在退款渠道最终成功后释放正式占用并刷新排期；退款申请或退款待确认阶段不释放。
异常或边界：
退款回调异常时订单保持“退款中”并触发运营提醒，商家端不得展示为已退款。
优惠券返还或下单奖励积分扣回失败时进入账本补偿队列，由后台异步处理，商家端展示处理中，不影响订单状态展示。

5.4 排期 / 预约管理
页面定位：管理门店营业日历、服务时段和可预约容量，保证分钟级预约时段正确锁定与释放，并向 C 端前台输出真实可约时段。
用户角色：商家管理员。
使用场景：商家每天根据实际营业安排维护可预约时间，保证前台用户看到的时段与门店实际产能一致。
履约模型定义：
上门接送型：上门与送回均使用商家自定义的分钟级时段；送回开始时间须不早于上门开始时间 + 120分钟，可跨天。
到店型：用户自行到店，但仍必须预约商家开放的分钟级可预约时段。
两种模型由服务项目的“履约方式”字段决定，排期日历按服务分别渲染，禁止混用。
核心功能：
以日历方式展示每日可约、已约、锁定和关闭时段。
商家直接按分钟精度自定义可预约时段，不采用平台固定60分钟粒度。
支持设置营业时间、休息日、临时停业和手动开放或关闭时段。
可查看当天订单与时段占用情况，并跳转到对应订单详情。(前期可不做)
支持跨天占用：寄养、过夜类服务可一次性占用连续多日的时段，日历以连续区块展示。
V1.0 排期由商家直接手工维护分钟级可预约时段，不做周模板或按营业时间自动生成的循环排期。
业务规则：
可预约时间精确到分钟；预约时服务端以时间区间 + 容量做原子锁定，锁定整体成功才视为预约成功。
临时锁定默认保留 10 分钟，超时自动释放；支付成功后转为正式占用，支付超时或订单关闭自动回收。
已有订单占用的时段不得关闭或降容量。
修改排期不影响已支付订单的快照与履约结果。
实际可预约容量 = min(商家配置容量, 当前可用服务人员数量)；服务时长不再换算固定60分钟槽位。
上门接送型服务的送回时段须满足 120分钟间隔约束，C 端已做置灰校验，商家端排期不得开放违反该约束的组合。
交互方式：
点击日期查看当天排期和订单占用。
点击时段可快速开放、关闭或调整状态；V1.0 不提供按周循环复制模板。
排期变更后首页待办和订单列表应同步刷新。
异常或边界：
并发抢约时以服务端锁定结果为准，商家端展示最终实际占用。
支付超时后临时锁定自动释放，商家端无需人工干预。
临时停业或关闭时段时若存在已占用订单，系统拦截并提示先处理订单。

5.5 服务项目管理
页面定位：维护门店对外提供的单次预约服务，是用户在前台预约下单的经营内容。
用户角色：商家管理员。
使用场景：商家创建单次预约服务并配置履约方式、价格、时长、人员要求与可预约时间。
核心功能：
支持新增、编辑、上下架服务项目。
V1.0 服务形态固定为“单次预约服务”。
维护服务名称、服务分类、履约方式、售价、划线价、时长、封面、简介、适用宠物类型、服务人员要求、备注和售后说明。
支持查看服务销量、预约量和当前售卖状态。
支持查看服务审核结果、驳回原因，并支持修改后重新提交审核。
服务内容由商家自行配置，前台按钮文案随配置自动切换。
V1.0 所有服务必须先选择预约时间后下单。
业务规则：
已支付订单引用的是服务快照，后续变更不得覆盖历史订单。

当服务仍有未完成订单时，仅允许下架，不允许删除。
所有单次服务统一走预约、支付、商家确认、履约与核销流程。
交互方式：
服务列表支持新增、编辑、上下架、查看状态和查看详情。
创建服务时选择履约方式（上门接送型 / 到店型），前台统一展示“预约下单”。

审核被驳回时列表展示驳回标签，点击进入可查看原因并修改重提。
异常或边界：
删除/下架服务前需要二次确认。
下架后，未完成订单仍按原快照履约。

页面定位：承接商家入驻申请、资料审核和门店档案维护，也是工作台开通前的基础能力。
用户角色：申请入驻用户、商家管理员、审核相关人员。
使用场景：用户准备开店时提交商家资质，审核通过后再进入日常经营。
核心功能：

5.8 平台订单核销
页面定位：处理用户在 C 端订单详情页出示的动态核销码，是平台自有订单从“待服务”流转到“已完成”的唯一入口。
用户角色：已授权核销权限的商家员工、商家管理员。
使用场景：用户携带宠物到达门店，或商家上门接送宠物时，用户在订单详情页出示动态核销码，员工扫码完成服务核销。
核心功能：
支持调用相机扫描用户订单详情页的动态核销码（条形码 / 二维码）。
支持手动输入订单号或核销码兜底，应对扫码失败场景。
扫码后展示订单关键信息，需二次点击“确认核销”才完成核销。
展示核销结果、核销时间、核销操作人和关联订单。
支持查询历史核销记录并按订单号、时间、操作人筛选。
业务规则：
核销必须由已授权商家员工操作，且核销人所属门店须与订单门店一致。
核销码有效期 5 分钟，每 5 分钟自动刷新；扫码时校验是否在有效期内、是否匹配当前订单、是否已被使用。
每次核销使用唯一请求号防重，同一订单只能成功核销一次。
核销成功后订单状态由“待服务”流转为“已完成”，核销码立即失效，同步开放 C 端评价与售后入口。
同一核销码 5 分钟内尝试核销失败超过 3 次，系统自动锁定该码 15 分钟并触发风控告警。
服务开始时间已过但未核销的，核销时系统提示“服务已开始，请确认是否继续核销”，需商家二次确认。
待服务订单和未创建退款单的售后中未核销订单均可核销；订单取消、改期或退款单创建成功后核销码失效。
交互方式：
点击首页或订单详情的“扫码核销”入口直接调起相机。
扫码后弹出订单确认卡片，展示服务名称、服务时间、客户昵称，商家确认后提交。
核销成功后展示成功页并提供“查看订单”“返回首页”入口。
异常或边界：
核销码已过期：提示“核销码已过期，请用户刷新后重试”，并引导用户下拉刷新生成新码。
订单已核销：提示“该订单已完成核销，不可重复操作”。
风控锁定：提示“核验失败次数过多，请 15 分钟后重试”。
商家端网络中断：核销请求超时不生成核销记录，核销码保持有效，支持重试或引导用户刷新。
用户端刷新失败：保留当前核销码并展示“刷新失败，点击重试”，不阻断商家重试扫码。

5.9 第三方团购核销
页面定位：处理美团 / 大众点评等第三方团购券的到店核销，不参与平台订单和资金口径。
用户角色：商家管理人员、已授权核销员工。
使用场景：顾客到店出示第三方券码，门店员工完成核销并记录结果。
核心功能：
支持扫描券码或手动输入券码进行核销。
展示核销结果、核销时间和操作人。
支持查询历史核销记录和结果回查。
支持查看当前门店已授权绑定的第三方平台及授权有效期。
业务规则：
核销必须由已授权商家员工操作。
每次核销使用唯一请求号防止重复。
第三方团购交易金额和结算不计入平台 GMV、营收或支付对账。
第三方团购不生成宠享家订单，其购买、查看券码、退款和售后均在来源平台处理。
C 端仅展示门店“支持核销”标识，不绑定第三方消费者账号、不导入第三方券包。
交互方式：
输入或扫码后立即返回核销结果。
核销失败时提供重试或回查入口。
异常或边界：
网络或接口异常时先做结果查询再重试，避免盲目重复提交。
授权失效时隐藏入口或提示重新授权。
5.10 售后管理
页面定位：统一承接用户针对本店订单提出的售后申请和投诉工单，商家只处理与自己门店相关的记录。
用户角色：商家管理员、门店店长。
使用场景：用户对已核销订单，或预约开始后未核销且商家拒绝退款的订单发起售后；商家提交说明和证据，运营最终裁决。
核心功能：
可查看售后 / 投诉工单列表、状态、关联订单、问题描述、证据和处理进度。
可提交商家说明、补充证据和处理意见。
支持按工单编号或订单号检索。
支持按处理状态、工单类型、诉求类型筛选。
支持查看运营最终处理结论及工单历史，不提供售后二次复审记录。
业务规则：
售后工单必须关联订单。已核销订单核销后7天内可发起；未核销订单须为预约已开始、商家已拒绝退款，且在预约开始时间起7天内。
同一订单同一问题只能存在一个处理中工单。
退款中或已全额退款的订单不再允许新建售后。
商家不可查看其他门店的售后内容。
商家对“退款”“部分补偿”类诉求可提交同意或异议意见，但最终结论由运营裁决；商家意见作为裁决依据入卷。
运营首次响应目标为 24 小时，超时系统提醒；商家补充说明的补充时限由运营在工单内设定。
交互方式：
工单详情中提交说明后同步更新给用户和运营端。
支持补充证据并跟踪处理状态。
异常或边界：
工单关闭后不可直接恢复。核销成功使当前未履约售后自动失效，用户可在核销后7天内针对新问题重新发起；部分退款成功后不可再售后。
重复售后按规则拦截。
用户申请金额超过订单实付金额时，系统已在 C 端拦截，商家端仅展示合规金额。

5.11 评价管理
页面定位：承接 C 端用户对门店、服务和服务人员的三维度评价，为商家提供服务质量改进依据与差评申诉通道。
用户角色：商家管理员、门店店长。
使用场景：商家查看用户对本次服务的评分与文字反馈，对中差评进行公开回复，对恶意差评发起申诉。
核心功能：
评价列表：按评分（全部 / 好评 / 中评 / 差评）、时间、服务、服务人员筛选。
评价详情：展示门店评分、服务评分、人员评分三个维度的星级，文字内容、图片、关联订单、评价时间与评价人。
商家回复：支持对每条评价公开回复一次，回复内容需过内容安全审核。
违规评价申诉：对涉黄、涉政、广告、恶意差评可提交申诉；每条评价最多申诉1次，由运营处理。
评分汇总：展示门店综合分、服务分、各服务人员评分均值及近 30 天趋势。
业务规则：
仅已核销订单可评价；已核销后部分退款仍可公开评价但不计分；未核销部分退款不可评价。一单一评，提交后不可修改。
评价期自核销成功起30天；售后中暂时隐藏。已核销后部分退款恢复评价但不计分；未核销部分退款不可评价。
仅有效完成订单评价计分；全退、未履约、部分退款均不计分。已核销部分退款评价可公开，未核销部分退款不可评价。
评价内容需经系统审核，违规内容不予展示；审核不通过的评价商家不可见。
商家回复仅一次机会，回复后不可修改或删除，仅可回复文字。
评分口径：单条综合评分 = 门店评分×40% + 服务评分×40% + 人员评分×20%；门店综合评分取近12个月有效评价均值并保留1位小数，少于5条显示“暂无评分”。已核销部分退款评价可公开但不计分；未核销部分退款不可评价。
交互方式：
从首页“待回复评价”指标卡、消息中心评价提醒均可直达评价列表。

5.14 经营数据中心
页面定位：为商家提供比首页指标卡更完整的经营分析，支持按时间维度复盘营收、订单、服务与客户表现。
用户角色：商家管理员、门店店长。
使用场景：商家按周或按月复盘经营情况，判断哪些服务值得加投、哪些时段需要补产能。
核心功能：
经营概览：营收、订单量、客单价、核销率、退款率、拒单率的核心指标与环比。
趋势分析：按日 / 周 / 月展示营收与订单量趋势，支持自定义时间区间。
服务分析：各服务项目的销量、营收、预约量、评价均分排行。
客户分析：新增客户数、复购率、客户消费分层。
服务人员表现：各人员的服务单量、评分均值、被指定次数。
排期利用率：各时段的历史占用率，辅助商家调整可约时段。
业务规则：
所有指标按单店维度统计，与首页看板使用同一口径，不得与平台整体数据混淆。
经营统计中的净营收应扣除已成功退款金额：全额退款订单不计入，部分退款订单按实付金额减成功退款金额后的净额计入；第三方团购不计入平台营收。
评价均分仅统计有效完成订单的评价数据。
数据按 T+1 更新，当日实时数据以首页指标卡为准。
数值正常为 0 时显示 0，接口异常或未取到数据时显示 --。
交互方式：
顶部时间选择器支持快捷区间（今日 / 近 7 天 / 近 30 天 / 自定义）。
各分析模块支持点击下钻到明细列表。
异常或边界：
新开门店无历史数据时展示引导空状态，不展示空白图表。
数据加载失败时保留页面框架并提供刷新入口。

7. 非功能性需求内容
性能：首页首屏应尽量在 2 秒内完成主要内容加载；订单、排期和服务列表切换应保持顺滑，避免明显卡顿；扫码核销从调起相机到返回结果应在 3 秒内完成。
可靠性：订单确认、拒单、核销、退款、改期和时段锁定等关键动作必须具备幂等能力，避免重复提交造成重复退款、重复核销或重复占用。
数据一致性：首页看板、订单列表、排期日历、评价汇总和数据中心必须使用统一口径；已支付订单的快照信息不得被后续编辑覆盖；改期必须原子交换新旧预约时段，失败时保留原预约。
权限与安全：按商家主体、门店和角色做权限隔离；敏感手机号、证件和结算信息需要脱敏展示；关键操作必须记录审计日志，包括接单、拒单、改期、退款、修改排期、核销、售后说明、评价回复、员工授权和店铺资料变更。
兼容性：优先适配微信小程序常见手机端分辨率和网络环境，弱网下应保留缓存并提供明确重试入口；扫码核销在弱网下须先查结果再重试，禁止盲目重复提交。
可用性：首页只保留高频入口和简易看板，避免复杂图表和长列表；空状态、异常状态和无权限状态都要有明确提示。
审计与追溯：所有状态变更需记录操作人、操作时间、操作前值与操作后值，审计日志保存期限按平台合规要求配置。
内容安全：商家提交的拒单原因、售后说明、评价回复、申诉理由与上传图片均须经过内容安全检查，违规内容拦截并提示。
消息通知：站内消息中心作为权威通知记录；同时接入微信公众号/订阅消息等微信外部通知能力（按实际账号资质与能力接入），用于待确认、自动接单、改期、退款、审核、售后和评价提醒。外部推送可关闭，推送失败时站内消息兜底。
并发控制：分钟级预约时段与容量锁定使用 Redis 原子操作，服务时长需校验对应预约时间区间及容量可用；并发改期与并发接单以服务端版本号为准。
第三方接口：对接美团 / 大众点评核销须使用正式授权机制、签名验签、密钥轮换、超时重试、幂等请求号和结果查询；完整券码与授权凭证不得写入普通日志或埋点。
数据安全：第三方核销记录独立于平台订单、支付、退款与结算数据；接口返回的商品金额仅作核销凭证展示，不计入平台 GMV 或营收。
