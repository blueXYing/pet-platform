# 宠物平台 V1.0 并发 / 故障注入测试矩阵 v0.1

> 定位：验证“并发时只能形成一个合法业务事实”和“基础设施失败后最终一致且不产生重复资金/履约副作用”。  
> 核心原则：退款单创建成功后禁止后续核销；核销先成功只使当前未履约型售后失效，并不永久禁止核销后的合法退款。

## 3. 核心并发不变量

任何压力/Chaos测试结束后都必须跑数据库断言：

```sql
-- 一单最多一个成功核销
SELECT order_id, COUNT(*)
FROM verification_record
GROUP BY order_id
HAVING COUNT(*) > 1;

-- 一单最多一张业务退款单
SELECT order_id, COUNT(*)
FROM refund_order
GROUP BY order_id
HAVING COUNT(*) > 1;

-- 一单最多一条评价
SELECT order_id, COUNT(*)
FROM review
GROUP BY order_id
HAVING COUNT(*) > 1;
```

以上结果必须全部为空。

同时验证：

```text
refund_order 已创建之后，不得出现 verified_at 更晚的成功核销事实
同一个 eventId + consumerName 不得成功消费两次
同一个 taskKey 不得存在两条任务
同一个 requestId 不能对应不同业务参数
```

## 4. VERIFY × CREATE_REFUND 竞态验收

必须做真实并发 Barrier 测试，而不是顺序模拟。

线程A：

```text
VerificationApi.verify
```

线程B：

```text
RefundCommandApi.createRefund
```

期望只可能出现合法结果：

```text
结果A：
refund_order先成功
→ verify失败 VERIFICATION_BLOCKED_BY_REFUND

结果B：
verify先成功
→ 若退款来源依赖当前未履约售后，则旧售后失效，refund创建失败
→ 若退款来源是合法核销后路径，则后续可以另行按合法来源退款
```

绝不允许：

```text
同一个“未履约售后竞态窗口”内
核销成功
+
基于已失效旧售后的退款也成功
```

## 5. PAYMENT_EXPIRE × CALLBACK 竞态验收

Barrier 同时启动：

```text
线程A PAYMENT_EXPIRE
线程B PaymentSucceeded callback
```

合法最终态：

```text
callback在关闭前被确认
→ 正常支付成功 → PENDING_CONFIRM

本地已确认PAYMENT_TIMEOUT关闭后才确认渠道成功
→ CANCELED底层事实保留
→ 自动LATE_PAYMENT_TIMEOUT FULL退款
→ REFUNDED
```

禁止出现：

```text
CANCELED + 正常OrderPaid接单链路同时成立
```

## 6. AutoConfirm × Merchant Action

至少压测：

```text
confirm vs auto-confirm
reject vs auto-confirm
reschedule vs auto-confirm
```

验证：

```text
CAS/version/confirmRound
```

任何一轮只允许一个合法终态。

## 7. Event / Outbox 不变量

随机注入：

```text
dispatcher崩溃
consumer执行前崩溃
consumer业务提交后重投
consumer某模块连续失败
多实例同时拉取
```

最终必须：

```text
资金事实不倒退
预约最终正确
优惠券最终正确
积分最终正确
评价scoreIncluded最终正确
站内强制通知最终存在
```

## 8. AsyncTask Chaos

测试：

```text
Worker claim 后 kill -9
lease过期接管
DB deadlock
执行成功但任务状态更新前进程终止
两台实例同时claim
服务停机跨过30min/24h
```

所有 Handler 都必须满足：

```text
at-least-once 执行
+
业务幂等
=
exactly-once business effect
```

注意这里的 exactly-once 是“业务效果”，不是消息系统物理只投递一次。
