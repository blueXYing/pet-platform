## 2. 代码证据链（当前 develop 树）

| 环节 | 位置 | 证据 |
| --- | --- | --- |
| 商家 24h deadline 生成 | `pet-refund-biz/.../RefundApplicationService.applyWithOutcome` | `deadline=now.plusHours(24)`，`refund_application.merchant_deadline` 落库；既有测试断言 `TIMESTAMPDIFF(HOUR,created_at,merchant_deadline)=24` |
| durable 超时任务注册 | `RefundApplicationService.timeoutSpec` + apply 内 `enqueue` | 任务键 `REFUND_MERCHANT_TIMEOUT:<applicationId>`，`availableAt=merchantDeadline`，retryPolicy=REFUND_APPLICATION，maxRetry=8 |
| 生产 worker 装配 | `pet-boot/.../config/RefundApplicationConfiguration.refundApplicationWorker` | `registration("REFUND_MERCHANT_TIMEOUT",...)` + `registration("REFUND_APPLICATION_CREATE",...)`，任务到期判定用 DB 时钟（`execute_at<=NOW(3)`，AsyncTaskMapper.xml selectClaimCandidate） |
| 超时自动批准 | `RefundApplicationService.handle(Timeout)` | 期限内 → `TaskResult(false, nextAt=deadline)`（worker 转 Retry，商家仍可处理）；到期且仍 PENDING_MERCHANT → `writeDecision(a,"AUTO_APPROVED",...)`，决定绑定准入 `refund.application.timeout`、requestId=`TASK:REFUND_MERCHANT_TIMEOUT:<app>`、`decidedAt>=merchantDeadline` |
| 退款单创建来源 | `RefundApplicationService.requireApproved` | AUTO_APPROVED 且绑定 `refund.application.timeout` → `source=MERCHANT_TIMEOUT_AUTO`（服务前即时批准走 `PRESTART_AUTO`，两者可区分，2026-10-05 用户裁决） |
| 全额原路退回 | `RefundApplicationService.createApproved` + `PaymentRefundService`/`RefundExecutionService` | `refund_type=FULL`、`refund_amount=原支付实付金额`、`initiator=SYSTEM`、channel=LAKALA 原路（payment_refund_dispatch 绑定原 payment_no/原渠道交易号）；渠道最终 SUCCESS 才发布 RefundSucceededEvent 并释放预约 |
| 商家期限内手动处理→NOOP | `RefundApplicationService.handle` 前置校验 | 非 PENDING_MERCHANT 时 `requireDecision + orders.requireDecisionRecorded` 后直接返回 done，不产生第二个决定 |
| 幂等 | command binding（refund_application_command）+ 重放校验 | 重复 handle/createApproved 命中 SUCCEEDED binding 原样重放；`reconcileTasks` 提供 MISSING/DEAD/CANCELED 任务恢复（既有验收覆盖） |

## 3. 新增测试证据（本次 PR）

`backend/pet-boot/src/test/java/com/petplatform/boot/booking/RefundMerchantTimeoutAcceptanceMySqlTest.java`（真实 MySQL，BOOKING_MYSQL_URL/AUTH_MYSQL_URL 同款环境变量，时钟搬移用 MySQL 会话时间，不用种子决定）：

1. `dueTimeoutTaskAutoApprovesAndCreatesOneFullOriginalRouteRefund`：
   - 期限内 worker `runOne()=EMPTY`（任务未到期不可领取）、`handle` 返回 `done=false,nextAt=deadline`（商家窗口仍在）；
   - deadline+1s（DB 时间）后真实 durable worker 触发 → `AUTO_APPROVED`，决定 requestId=`TASK:REFUND_MERCHANT_TIMEOUT:<app>` 且 `decided_at>=merchant_deadline`；
   - worker 第二跑经 `REFUND_APPLICATION_CREATE` 创建退款单：`source_type=MERCHANT_TIMEOUT_AUTO`、`refund_type=FULL`、`initiator_type=SYSTEM`、`refund_amount=128.00`（=原实付）、channel=LAKALA；
   - 渠道执行一次成功：`payment_refund_dispatch.state=VERIFIED_SUCCESS` 且 `refund_amount=original_paid_amount`（全额）、`refund_transaction` 恰一条 REFUND；RefundSucceededEvent → 订单 `refunded_amount=128`、预约 RELEASED、审计 REFUND_RELEASE；
   - 重放幂等：worker `EMPTY`、`handle` 重放 done、`createApproved` 重放同号、sends/decision/refund 计数不变。
2. `merchantDecisionInsideTheWindowMakesTheTimeoutTaskANoop`：商家 APPROVE 后超时任务照常触发 → `NOOP`（仍 APPROVED、决定唯一、无 AUTO_APPROVED），退款单来源=`MERCHANT_APPROVED` 而非 `MERCHANT_TIMEOUT_AUTO`。

既有补充证据（同包，已在 CI 门禁内）：`RefundApplicationAcceptanceTest.earlyTimeoutRetriesAndExactDeadlineExcludesMerchant`（早触发 Retry、到期后商家被拒 REFUND_MERCHANT_DEADLINE_PASSED、handle 幂等）、`simultaneousOwnerAndDueTimeoutHaveOnlyOneDecision`（商家与超时并发仅一个决定）、`duePendingMissingDeadAndCanceledTimeoutTasksRecoverFromRealApplication`（任务缺失/死亡/取消恢复）、`bothOrdinarySourcesUseOriginalChannelAndOnlyFinalSuccessReleases`（MERCHANT_TIMEOUT_AUTO 与 MERCHANT_APPROVED 双来源渠道终态一致）、`preServiceAutoSourceIsDistinctFromMerchantTimeoutSourceOnRefundOrders`（PRESTART_AUTO 与 MERCHANT_TIMEOUT_AUTO 可区分）。

## 4. 边界与遗留风险

- 本核实不覆盖真实支付渠道 HTTP（渠道边界为签名/验签脚本替身，与全链其他验收一致）；原路退回以 `payment_refund_dispatch` 绑定原支付要素为证据。
- `pet.refund.application.enabled/worker.enabled` 生产开关默认关闭；本核实证明的是链路正确性，不含生产启用动作。
- 在途 PR #172（处置动作）改动 refund 域部分文件（ADMIN_ABNORMAL_CLOSE source 族、V32 迁移、outbox 忽略集），与本测试基于同一 develop 基线，交集由主会话合流做并集；本测试文件独立命名，无生产代码冲突面。
