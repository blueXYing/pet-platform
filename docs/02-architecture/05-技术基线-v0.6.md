# 宠物平台 V1.0 技术基线 v0.6

> 文档定位：将产品 SSOT 转换为研发可执行的技术状态机、字段字典、模块边界和跨模块通信契约。
> 
> 优先级：产品 SSOT > 本技术基线 > 各模块实现。若技术实现与产品 SSOT 冲突，先回到产品裁决，不允许代码自行定义产品规则。

---

## 1. 技术架构原则

### 1.1 形态

V1.0 采用 **模块化单体（Modular Monolith）**，Spring Boot 单进程部署；模块边界按未来微服务拆分方式设计。

### 1.2 模块通信

强制规则：

- `xxx-biz` 只能依赖其他模块的 `yyy-api`。
- `xxx-biz` 禁止直接依赖其他模块的 `yyy-biz`。
- 跨模块禁止访问对方 Repository / Mapper / DO / Entity。
- `*-api` 只允许放：API Interface、Command、Query、DTO、Contract Enum、Error Code。
- `*-api` 禁止放：数据库实体、Mapper、Repository、Service 实现、MyBatis 注解。
- 当前单体由 `LocalXxxApiImpl` 实现 API。
- 未来微服务由 `FeignXxxApiAdapter` 实现同一 API 契约，调用方业务代码原则上不改。

### 1.3 同步与异步

同步 API 用于：

- 查询必要业务事实；
- 执行必须立即得到成功/失败结果的业务命令；
- 获取并发操作许可；
- 预约容量校验与资源锁定。

集成事件用于：

- 支付成功；
- 退款成功；
- 核销成功；
- 订单完成；
- 售后裁决；
- 商家下线；
- 评价创建；
- 需要通知、积分、优惠券等后续处理的事实广播。

V1.0 即引入 **Transactional Outbox**，避免未来从本地事件迁移 MQ 时大改业务代码。

## 3. 基础字段规范

### 3.1 ID

- 主键：`BIGINT`，Snowflake。
- 订单号：`BIGINT`，Snowflake。
- 退款单号：`BIGINT`，Snowflake。
- Java：`Long`。
- API / JSON / TypeScript：统一按 `String` 传输，禁止 JS Number。

### 3.2 时间

- MySQL：`DATETIME(3)`。
- 后端内部统一 Instant / OffsetDateTime 语义。
- API 返回 ISO-8601 字符串。
- 业务时区统一配置，不允许代码中散落硬编码时区。

### 3.3 金额

- 金额：`DECIMAL(18,2)`。
- 比例：`DECIMAL(10,6)`。
- Java：`BigDecimal`。
- 禁止 float / double 参与资金计算。

### 3.4 状态

- DB 状态字段：`VARCHAR(32)`。
- API 使用稳定英文 code。
- 前端中文文案通过状态映射展示，不把中文状态作为数据库值。

### 3.5 并发

交易主表统一保留：

```text
version BIGINT NOT NULL DEFAULT 0
```

用于乐观锁；退款创建 × 核销采用更强的订单操作互斥机制。

### 3.6 删除

- 订单、支付、退款、核销、售后、积分流水、优惠券流水、评价、审计日志：禁止物理删除。
- 配置/主数据按需要使用 `deleted_at` 或启停状态。

### 3.7 支付超时关闭后的迟到支付

产品规则：

```text
支付超时关闭
+
渠道随后确认真实支付成功
→ 原订单保持关闭
→ 系统自动按渠道实际支付金额全额原路退款
```

技术要求：

```text
order_stage 保持 CANCELED
payment_status 投影可更新为 PAID
不得转 PENDING_CONFIRM
不得恢复预约
不得创建 late_payment_recovery
不得要求用户重新选择预约时间
不得重新占用优惠券
```

迟到支付成功：

```text
LatePaymentSucceededAfterTimeoutEvent.v1
→ refund-biz
→ FULL refund_order
→ refund_source = LATE_PAYMENT_TIMEOUT
```

不得产生正常 `OrderPaidEvent`，所以：

```text
不创建 30 分钟自动接单任务
不确认预约资源
不消费优惠券
不奖励正常下单积分
```

退款成功后展示态按既有退款优先级变为 `REFUNDED`；底层 `order_stage=CANCELED` 保留。

## 4. 产品展示状态与技术状态分层

产品 SSOT 中的：

```text
待支付 / 待确认 / 待服务 / 已完成 / 已取消 /
退款待确认 / 退款中 / 已退款 / 部分退款 / 售后
```

定义为 **DisplayOrderStatus（产品展示态）**。

数据库不使用单一字段承载全部含义，而拆为多个事实状态。

### 4.1 OrderStage

```text
PENDING_PAYMENT
PENDING_CONFIRM
PENDING_SERVICE
COMPLETED
CANCELED
```

语义：订单底层履约阶段。

### 4.2 PaymentStatus

```text
INIT
PAYING
PAID
FAILED
CLOSED
```

支付渠道原始状态另存，不直接等于平台支付状态。

### 4.3 RefundApplicationStatus

退款申请与真正的渠道退款单分开。

```text
PENDING_MERCHANT
APPROVED
AUTO_APPROVED
REJECTED
```

- 服务开始前：AUTO_APPROVED。
- 服务开始后：PENDING_MERCHANT。
- 商家同意：APPROVED。
- 商家 24 小时超时：AUTO_APPROVED。
- 商家拒绝：REJECTED。

### 4.4 RefundStatus

只表示已经创建的业务退款单：

```text
CREATED
PROCESSING
SUCCESS
FAILED
UNKNOWN
```

`refund_order` 创建成功，是“永久禁止核销”的业务边界。

### 4.5 RefundType

```text
FULL
PARTIAL
```

普通商家退款只能 FULL；PARTIAL 仅由运营售后裁决产生。

### 4.6 AfterSaleStatus

```text
PENDING
PROCESSING
WAITING_SUPPLEMENT
RESOLVED
INVALIDATED
WITHDRAWN
CLOSED
```

没有 AFTERSALE_REVIEW / SECOND_APPEAL。

### 4.7 AfterSaleDecision

```text
FULL_REFUND
PARTIAL_REFUND
REJECT
RESERVICE
OTHER_NON_REFUND
```

### 4.8 VerificationStatus

订单投影字段只保留：

```text
UNVERIFIED
VERIFIED
```

“退款已创建禁止核销”不新增第三个永久状态，由退款事实 + 操作互斥判断。

风控临时锁定使用 `verification_lock_until` 单独表达。

### 4.9 AppointmentReservationStatus

```text
TEMP_LOCKED
CONFIRMED
RELEASED
EXPIRED
```

退款申请、退款待确认、退款处理中均不释放正式预约；只有渠道退款最终成功才释放。

## 5. DisplayOrderStatus 计算优先级

后端统一计算，C 端/商家端/运营端禁止自行拼状态。

优先级：

```text
1. refund.type = FULL && refund.status = SUCCESS
   => REFUNDED / 已退款

2. refund.type = PARTIAL && refund.status = SUCCESS
   => PARTIAL_REFUND / 部分退款

3. refund.status in (CREATED, PROCESSING, UNKNOWN)
   => REFUNDING / 退款中

4. active_refund_application.status = PENDING_MERCHANT
   => REFUND_PENDING_CONFIRM / 退款待确认

5. active_aftersale.status in (PENDING, PROCESSING, WAITING_SUPPLEMENT)
   => AFTERSALE / 售后

6. order_stage = PENDING_PAYMENT
   => PENDING_PAYMENT / 待支付

7. order_stage = PENDING_CONFIRM
   => PENDING_CONFIRM / 待确认

8. order_stage = PENDING_SERVICE
   => PENDING_SERVICE / 待服务

9. order_stage = COMPLETED
   => COMPLETED / 已完成

10. order_stage = CANCELED
    => CANCELED / 已取消
```

## 8. 订单并发互斥模型

### 8.1 目标

`VERIFY` 与 `CREATE_REFUND` 在并发执行时必须串行化，但两者不是永久对称互斥。

已经封板的产品语义是：

```text
refund_order 先创建成功
→ 从此禁止后续核销

核销先成功
→ 仅使“当前未履约型售后”失效
→ 不等于永久禁止所有后续合法退款
```

例如：订单已核销后，用户仍可进入正常的核销后退款/售后流程；商家同意全额退款，或新的核销后售后裁决产生退款时，仍允许创建退款单。

因此 `order_operation_guard` 的职责是防止同一时刻的关键事实竞态，而不是实现“核销后永远不可退款”规则。

### 8.2 order_operation_guard

由 order 模块拥有。

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | Snowflake |
| order_id | BIGINT | 订单 ID |
| operation_type | VARCHAR(32) | VERIFY / CREATE_REFUND |
| token | VARCHAR(64) | 本次操作令牌 |
| status | VARCHAR(16) | ACQUIRED / COMMITTED / RELEASED / EXPIRED |
| expire_at | DATETIME(3) | 临时锁到期时间 |
| created_at | DATETIME(3) | 创建时间 |
| updated_at | DATETIME(3) | 更新时间 |

约束：同一订单同一时刻只能存在一个 ACQUIRED 操作许可。

### 8.3 当前单体执行

退款：

```text
acquire CREATE_REFUND
→ 重新读取订单、退款申请、售后来源事实
→ 按退款来源执行资格校验
→ 创建 refund_order
→ commit guard
→ order.refund_order_id = refund_order.id
```

来源校验必须区分：

```text
1. 服务开始前自动退款
   → 通常要求尚未核销

2. 服务开始后商家同意 / 24h 超时自动退款
   → 允许在申请后发生核销；核销本身不自动否决该退款路径

3. “未履约型售后”裁决退款
   → 如果核销已经先成功，该旧售后应先 INVALIDATED，禁止再基于旧售后创建退款

4. 核销完成后新发起的正常售后
   → 在核销后 7 天资格内，运营仍可裁决全额/部分退款
```

禁止使用简单的 `verification_status == VERIFIED => 不可退款` 规则。

核销：

```text
acquire VERIFY
→ 校验 refund_order_id 为空
→ 校验尚未核销且订单仍可履约
→ 写 verification_record
→ mark order VERIFIED/COMPLETED
→ commit guard
→ 使当前“未履约型售后”失效
```

任一步失败：release guard。

### 8.4 未来微服务

`OrderOperationGuardApi` 的调用契约保持不变，只把 Local 实现换成 Feign 实现。

处于临时 PREPARE/ACQUIRED 状态时，另一操作返回“业务繁忙，请重试”，不是永久业务禁止；只有 `CREATE_REFUND` commit 后才形成正式的“禁止后续核销”边界。`VERIFY` commit 后只会使当前未履约型售后失效，不得被实现为“禁止所有未来退款”。
