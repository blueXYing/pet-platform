## 1. 终端与技术栈

| 交付物 | 固定方案 | 本期范围 |
|---|---|---|
| 微信小程序 | Taro + React + TypeScript；Taro页面路由与平台API | 一个AppID、一个构建/发布入口；宠物主与商家工作区切换 |
| 运营网页 | React + TypeScript + Vite + React Router | 独立PC Web，调用既有Java后端 |
| App | 后续单独评审 | 不创建App工程、不提前选择React Native |

本期无用户Web/H5、独立商家Web或第二个商家小程序。小程序不是将ReactDOM网页嵌入WebView。后端Java21/Spring Boot模块化单体、MySQL/Redis、MyBatis、Snowflake、金额精度、Outbox、durable AsyncTask及全部交易规则不变。

Taro/React/TypeScript/Node及包管理器的准确版本由C-001、A-001在获准开发后验证并写入版本记录与锁文件；不以latest作为最终锁定版本。未验证的包版本不声称可构建。小程序与运营端可选各自兼容版本，不强行同步React主版本。

状态管理使用React局部状态与受控上下文起步，不再使用Pinia；复杂共享状态库另评估。Web和小程序共享契约语义，平台请求/路由实现分别适配。小程序素材和页面按分包及按需加载安排，具体包体限制以实施时平台规则核验，不猜测固定配额。

## 2. 目录与唯一所有权

```text
backend/                         后端，不变
frontend-miniapp/                唯一小程序工程
  config/                       构建配置
  src/app*                      应用入口与全局配置
  src/consumer/                 用户工作区
  src/merchant/                 商家工作区（普通分包）
  src/shared/                   登录、请求、UI基础、公共素材及契约索引
frontend-admin/                  运营React网页
e2e/                            Web、小程序、视觉与跨端测试
```

- C-001由C-End负责唯一应用壳、consumer与shared；不实现merchant业务。C-End负责小程序根配置、package.json、锁文件、app入口、shared的默认写所有权。
- M-001由Merchant负责src/merchant/**，使用C-001基线；不得创建第二套package.json、登录壳或AppID。M-001依赖GOV-001与C-001；完成C-001后，后续C/M工作区可并行。未完成时只能在原任务下做只读协作，不谎报依赖解除。
- Merchant需要共享配置/组件/素材变更时，由C-End在关联Issue内作为唯一编辑者处理，记录提交及释放；Merchant不直接并发编辑共享文件。需要越出Allowed Modules时先由Work记录授权，不能靠共享目录名获得默认权限。
- 运营端由Admin负责frontend-admin/**。QA拥有e2e及既有架构/CI范围，不直接改前端业务代码。
- frontend-c/与frontend-merchant/仅保留历史迁移说明，不再作为开发目标，不生成旧栈脚手架。
- 六个岗位保留；一个Issue一个短生命周期Thread，代码Issue必须独立branch/worktree，依赖/共享文件未解锁不得为凑并发抢跑。

## 3. 会话、身份与服务端边界

沿用商家PRD §5.2：默认宠物主，个人中心进入商家工作台；切换工作区不退出登录，每次进入重新校验最新准入与权限；审核/签约/门店/子账号状态遵循原PRD及SSOT，门店下线不得阻断规定的存量履约与售后。

保留/api/v1/c、/merchant、/admin分区；服务端验证登录身份、门店、动作和数据范围，前端切换标志不产生授权。深链或手工构造请求也须验证。

缓存与在途请求至少隔离用户、商家、门店和当前工作区；切换、退出或权限撤销后旧结果不能写入新上下文。小程序微信登录、支付、扫码、上传均通过平台适配层；运营端会话和缓存不与小程序混用。

具体会话DTO、权限结果、失效/刷新及是否需要切换命令等尚未冻结，进入CCR-ACR-001，由AUTH-001承接契约建立与评审。批准R4是批准补齐契约方向，不是假定具体API/Schema已获批准。工程壳可使用内部注入的测试fixture，不暴露为公共API契约；真实接入及生成公共SDK必须等待CCR批准。

所有ID和HTTP金额保持字符串；业务写请求带X-Request-Id；展示状态和actions由服务端返回，前端不复制DisplayOrderStatus状态机。前端框架切换不修改交易、权限和退款产品规则。
