# 43-确认支付半屏与订单快照名称裁决补充 v1.0

状态：产品规则批准（2026-11-27 用户裁决）。本文件是裁决记录与验收定义，不代表已上线。

## 1. 背景与来源

用户 2026-11-27 对照小程序“确认支付”页截图与设计稿 Figma 690:4837《确认支付》：

> “现在小程序支付 … 和 figma … 的支付有点不一样，小程序直接可以不用选择微信还是支付宝 直接调用微信，但是这个地方 figma 是实现的支付方式半屏，而我们图片中的比较丑陋”

## 2. 裁决

- **确认支付改为真正的底部半屏**（用户在“真正的底部半屏 / 独立页面照半屏版式重排”中选了前者）：预约成功后与订单详情“去支付”都在当前页面弹出、背景压暗；原独立页面保留作兜底入口。版式按 Figma 690:4837：标题与关闭、浅蓝摘要卡（店铺名 / 服务 / 实付金额）、支付方式行、蓝色胶囊按钮。
- **小程序仍不展示支付方式选择**（HTTP 契约 10：“C 端小程序 V1.0 不展示支付方式选择”，不变）：半屏只显示固定的“微信支付”一行并呈选中态，不显示支付宝，不做切换。
- **订单详情接口带店铺名**（用户在“多查一次门店显示店铺名 / 只用订单已有信息 / 改订单接口带店铺名”中选了后者）：`GET /api/v1/c/orders/{orderId}` 增补 `storeName`、`serviceName`，取自下单时订单域自己写入的快照（06 号 `order_service_snapshot`），不回查商家 / 服务存储；仅详情携带，列表项不带；订单无快照行时为 null。见 HTTP 契约 10 §3.7、OpenAPI 11 `OrderDetailData`。
- 支付流程硬规则不变：真实模式调起微信支付，绝不本地虚构“已支付”态，支付终态以服务端订单为准（40 号裁决、CCR-PAY-CENTER-001 阶段 7）。

## 3. 执行位置

- 小程序：`frontend-miniapp/src/consumer/components/pay-sheet/`（半屏组件）；入口 `components/booking-sheet/booking-sheet.tsx`、`pages/orders/detail.tsx`；兜底页 `pages/booking/pay.tsx`。
- 后端：`OrderQueryApi#getOrderNames`、`OrderQueryService#getOrderNames`、`OrderQueryMapper.xml#selectSnapshotNames`、`COrderQueryController#detail`。

## 4. 兼容与已知限制

- C 端订单解码器是严格键集（未知键失败关闭）：小程序必须与后端同批发布，先单独发后端会让旧版小程序的订单列表 / 详情读取失败。V1 尚未上线，按同批发布处理。其余客户端忽略新字段无影响。
- 设计稿里的“支付宝”一行在小程序中不实现（微信小程序内不能调起支付宝，契约亦规定不展示选择）。

## 5. 验收要求

1. 预约成功后点“去支付”，当前页面弹出确认支付半屏、背景压暗；摘要卡显示店铺名、服务名、实付金额。
2. 订单详情里对未支付单点“去支付”，同样在当前页面弹出半屏；关闭后订单详情不受影响。
3. 半屏支付方式只有“微信支付”一行且为选中态，没有支付宝，也没有切换交互。
4. 点“确认支付”走原有微信支付调起；取消或失败时提示可重试，页面不出现“已支付”。
5. `GET /api/v1/c/orders/{orderId}` 返回 `storeName` / `serviceName`；列表接口不带这两个字段；非本人订单仍为统一的 404。
