# V1 商家入驻签约：人工裁决补充

状态：人工已批准。来源：用户于 2026-09-17 对 OD-W0-002 作出三点明确决定。本文件为原 PRD
（商家端 §5.2/6.6、运营 §5.1/6.2.1、C端 §5.1.23 涉及"支付服务商签约"处）的增量裁决，
不重写原 Word 历史文件。

## 裁决条款

### D1 签约性质：平台与商家之间的电子协议

PRD/草案所称"支付服务商签约"**不是**与任何第三方支付服务商（拉卡拉或其他）的进件、
渠道对接或签约 API 集成，其实质是**平台与商家之间签署的电子协议**（商家版用户协议，
含支付服务相关条款）。V1 不选择、不集成任何外部签约 Provider；拉卡拉仅按原文存在于
支付/回调语境，属 OD-W0-001 资金范围另行裁决，与入驻签约流程无关。

由此：入驻签约无外部 API、回调、凭据、沙箱或渠道协议依赖；不存在"待第三方通道返回"
的中间态来源。

### D2 签约完成判定：商家勾选同意即成功

商家在端内阅读协议后，**勾选并点击"同意"即签约成功**。生效路径为
`未签约 →（阅读协议并勾选同意）→ 已签约`。

- 同意动作是带 `X-Request-Id` 的幂等写操作，同 requestId 重放返回原结果；
- 同意记录须留存**协议版本号、同意时间、操作账号**供审计（子账号不得代主账号签署，
  沿用商家 PRD"子账号不得查看或修改主账号结算与签约信息"原文）。

### D3 工作台准入映射：按 PRD 原文执行（人工确认）

- 审核通过且签约（协议同意）完成后，开通商家工作台；
- 已通过审核但未签约的账号进入时，提示先完成签约并展示签约入口；
- 每次进入工作台前校验四态：入驻审核状态、签约状态、门店冻结状态、子账号启用状态；
- 下线停止新订单/新预约，旧订单继续履约，存量退款/售后按SSOT §15及原权限、交易硬规则处理（2026-09-17后续人工确认）；不以“仅可查看”统一拦截存量履约。
- 冻结保留已定读取能力，冻结写动作仍待裁决；本次下线确认不扩大冻结权限。

### D4 协议版本更新（2026-09-17后续人工确认）

V1不新增强制重签。已签商家保持原协议效力，发布新版不会自动撤销工作台资格；新版用于后续首次签署。已发布内容不可覆盖，必须保留原版本和同意记录。具体接口、存储与主账号真实USER操作者映射已由本轮技术契约确认，见27号商家域契约补充；不因此宣称功能已实现。

## 对 PRD 状态机的影响

商家 PRD §6.6 签约状态枚举（未签约/签约中/已签约/签约失败）**保留**，展示与文案能力不删；
但电子协议模式下，"签约中/签约失败"无自然触发路径（其原触发事件"通道异常或资料不一致"
源自外部通道语义，V1 不存在）。V1 生效路径仅 D2 一条；失败原因/重试 UI 预留以兼容后续
若引入外部流程，V1 不构造失败场景、不虚构失败原因。

原 PRD 中"支付服务商签约"字样在后续 PRD 修订时统一同步为"入驻协议签署（电子协议）"表述；
修订前以本裁决为上位解释。

## 解除与保留

- **解除**：OD-W0-002 对 MER-001（商家/门店/人员契约）、M-002（商家端工作台/入驻页）、
  A-002（治理动作）的阻塞；相关契约冻结按 CCR 流程另行执行，本裁决不等于开发启动批准。
- **已确认子项**：协议版本管理与换版后是否重新同意按D4执行；协议文本内容仍由运营侧维护，不在本裁决编写。
- **保留**：OD-W0-001（资金冻结/分账/提现/保证金）独立未决；支付回调验签等支付链路事项
  不因本裁决批准或实现。

## 验收要求

1. 审核通过且协议已同意 → 工作台开通；未同意 → 提示签约并展示入口，无法进入经营类功能。
2. 同意操作幂等（同 requestId 重放返回原结果）；审计可查协议版本、同意时间与操作账号。
3. 入驻签约链路无任何第三方支付服务商 API/回调/凭据依赖，不因缺少外部通道阻塞入驻。
4. 进入工作台的四态校验按 PRD 执行；子账号不能签署或查看主账号签约信息。

本文件为产品裁决记录与验收定义，不声明任何功能已实现；实现与验收由后续 MER-001/M-002/A-002
阶段交付。
