# V1 验收期人工裁决补充（2026-11-17 ～ 2026-11-23）

状态：人工已批准。来源：用户在 2026-11-17 ～ 2026-11-23 的人工验收会话中逐条提出并确认；下文“来源”引用用户原话，标注“转述”的为对原话的概括。本文件是原 PRD、AUTH 草案与商家入驻契约的增量裁决，不重写历史文件；仅调整下列各条，其余封板规则不变。

## 一、小程序登录态（2026-11-18）

- 规则：小程序 access 会话默认有效期由 15 分钟调整为 7 天（604 800 秒），作为代码默认值，所有环境一致，仍可由配置覆盖。
- 原因（转述）：15 分钟导致真机验收中频繁静默重登。
- 执行位置：`CAuthProperties.accessTtlSeconds`；`docs/04-api/10-HTTP-API-Contract-v0.4.md` 的会话行。

## 二、运营端登录态与会话（2026-11-20）

来源：“我点击刷新后 每次都需要我重新登录 很烦人，并且我希望把我的运营端的过期时间也设置的长一点 现在太短了”；“我希望此次的过期时间长不仅仅针对此次的部署，而是以后只要我随意启动项目 都是如此”。

- 刷新或重开浏览器保留登录态：令牌保存在浏览器本地存储，退出登录或服务端拒绝时立即清除。每次整页加载都用该令牌向服务端重新校验会话与权限；被拒即关闭访问，不渲染任何业务页。
- 无操作过期：30 分钟调整为 12 小时（代码默认值）。
- 登录验证不再要求最短 8 位密码（为使验收账号 `admin/admin` 可登录；存量密码的强度以创建时为准）。创建或修改密码的门槛不变：至少 8 位，且含大写、小写、数字、其它字符中的至少三类。
- 验收环境固定账号 `admin/admin`：仅 E2E 验收服务器（`E2eCoreLoopServer`，测试源码）在启动时幂等创建，生产装配不包含。
- 不变：后端 RBAC 与数据范围、服务端最终授权、审计、脱敏、原因/用途。
- 执行位置：`frontend-admin/src/App.tsx`、`AdminAuthService.ADMIN_SESSION_IDLE_SECONDS`、`AdminPasswordHasher.require / requireInitialStrength`、`E2eCoreLoopServer.ensureAdminAccount`。

## 三、入驻申请材料随时可查（2026-11-20）

来源：“还有就是 我认为这里不应该加什么 一次性查看，而是可以随时查看，因为后期运营会进行查看，而不是只有审核的时才会查看”；“图片中审核通过 在我圈起来的部分 他这个地方展示的是在额没有审核的，看起来有点别扭”；“还有就是这个地方的 已经通过了 ，这个地方还是未查看”。

- 查看材料不再要求填写理由，不再有“申请一次性查看”门槛：点击即看，审核中与审结（通过或拒绝）后均可随时查看。
- 每次读取仍在服务端申请一次性授权、带水印并逐次记入审计。
- 审结后的申请：任何具备查看权限的运营都可读取；任务归属校验只在审核中生效。
- 审结后的申请不再显示“未查看”标签，步骤条不再显示“0/N 份已看”。
- 执行位置：`ReviewDetailPage.tsx`、`MerchantApplicationService`（读授权门槛）。

## 四、入驻申请报错必须说清原因（2026-11-20）

来源：“这个接口报错了 curl … /manual-verification … COMMON_INVALID_ARGUMENT”；“这里的参数校验失败了 你要给出正确的参数错误，而不是这种笼统的操作失败错误，然人根本不知道是什么参数错误或者是出现什么错误”；“… /decision … COMMON_DEPENDENCY_UNAVAILABLE protected value provider is unavailable 还是一样的啊”。

- 证件与主体校验、人工核验、审核决定等失败时，服务端返回具体的中文原因（卡在哪一项、下一步做什么）；运营端原样展示服务端原因，不折叠成“操作失败”。
- 错误码与 HTTP 状态语义不变。

## 五、重复人工核验（2026-11-20）

来源：“就是我之前已经提交过 人工校验了 。现在还需要重新提交。还是说直接提交审核决定”；“接口报错 … /decision … COMMON_CONFLICT submitted revision requires exactly one verified CREDIT_CODE evidence”。

- 问题：旧实现每提交一次人工核验就新增一批证据行（登记未变时只跳过登记），同一版本上重复核验后证据多条，批准被“恰好一条已核验证据”卡住。
- 新规则：内容未变的重复核验不新增证据行；改值重核时新登记生效，旧登记转为已释放（RELEASED），旧证据保留为历史；批准闸门只认“当前有效登记引用的证据”。
- 实现细则（未经单独裁决，用户知情后可改）：行业许可证没有主体登记，同一版本上多次核验时以最近一次为准；任何历史登记与证据都不删除。

## 六、商家协议管理与签约（2026-11-20）

来源：“肯定是要做的。首先需要考虑这几个事情。1:这个协议采用什么格式？文件，还是说怎么回事 2:就是不要把版本链弄的太严厉了因为在实测下来会有很多的麻烦最好 不要进行强关联”；“如果说是纯文本 那么这里的格式怎么突出呢”；“这里应该展示的是阅读模式，并且我希望能生成一版正式的协议放入到sql 保证我下次部署的时候能有这个协议初始化，而不是需要自己去填写”。

- 协议正文采用 Markdown 编辑；运营端与小程序端都以阅读模式展示，不显示源码。
- 运营端“协议管理”：编辑、发布、查看版本历史；发布即切换当前生效版本。权限沿用 `merchant.application.decide`（V1 单运营 RBAC；后续拆分专属动作码时另行登记）。
- 版本链松耦合：签署请求中的版本号与内容哈希是可选的客户端提示值，形态合法即不再因与当前版本不一致而拒绝（原 409）。受理记录以签署那一刻的当前版本为准，留存版本、哈希、时间与账号。
- 与 SSOT“协议换版”一致：已签商家保留原协议效力，不强制重签；已发布版本内容不可覆盖。
- 首次部署自带正式协议：E2E 验收服务器内嵌正式协议模板。
- 执行位置：`AdminMerchantAgreementController`、`MerchantAgreementService`、`frontend-admin/src/pages/AgreementAdminPage.tsx`、小程序 `signing.tsx` 与 `markdown-lite.ts`。

## 验收要求

1. 运营端刷新后仍是同一账号；服务端拒绝的旧登录态在刷新时被关闭访问；退出后回到登录页。
2. 运营端 12 小时内无操作不掉线；创建账号仍拒绝弱密码。
3. 入驻申请在审核中与审结后均可查看材料；每次读取有审计记录。
4. 同一申请重复提交人工核验后，批准不再被“证据多条”卡住；历史登记与证据保留，可审计。
5. 运营发布新版协议后，未签约商家的首次签署不被拒绝，受理记录指向签署时刻的当前版本。
6. 新环境执行初始化 SQL 后，首页活动与三块内容位即有数据。
7. 新环境按建库清单执行后，首页有三张活动卡与三块内容位；三张活动卡是平台活动（不关联商家），点进落地页不显示空的商家列表。
