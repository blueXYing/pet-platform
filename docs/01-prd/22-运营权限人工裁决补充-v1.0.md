## 1. 人工选择及生效规则

| 项目 | 人工意见 | 正式规则 |
|---|---|---|
| P1 | A | 统一六个角色名称：运营编辑、审核员、运营管理员、财务只读、审计只读、平台超级管理员。角色是RBAC配置，不要求配六名人员 |
| P2 | 原PRD未写财务则不考虑；已有财务也以RBAC分配 | 原PRD确有财务（§4.1/4.2），因此只在既有V1能力内通过RBAC配置查看/执行权限；不新增独立财务执行角色或财务专用审批流程，不因角色存在新增资金功能 |
| P3 | 只考虑单运营，不考虑双运营 | 具备售后裁决权限的一个运营账号可直接作首次正式裁决；不等待第二运营拟批/复核。退款仍按渠道结果与既有并发规则执行 |
| P4 | 不考虑双运营 | V1不实现双人复核、第二人审批、事后第二人复核或提交人与复核人隔离门槛，包括权限变更；获授权账号单人执行 |
| P5 | 运营编辑直接操作，无需审批 | 获得编辑/发布权限的运营编辑可直接编辑并发布平台内容/公告，无内部提交后待审批阶段 |
| P6 | B | 平台超级管理员默认拥有全部已批准V1业务动作和全平台数据范围；不绕过业务状态、金额、脱敏与审计约束；不因旧P6-B文字恢复P4已取消的双人复核 |

P2为用户自定义裁决，不记作原草案P2-A或P2-B。P3/P4/P5同样按本次明确要求，不套用原草案里仍保留双人的备选。

## 2. RBAC授权模型与职责

功能/动作权限和数据范围分别控制，页面按钮不是安全边界。除超管默认全权限外，账号实际能力由已分配角色的权限配置决定，不按角色中文名称硬编码。以下为既有职责整理，不建立不可调整的硬限制或新的业务接口。

| 角色 | 默认职责方向 | 配置原则 |
|---|---|---|
| 运营编辑 | 平台内容、百科/基础资料、公告等已授予的编辑与发布 | 可直接生效，不要求另一人审批；不因能发公告自动获得退款权限 |
| 审核员 | 商家准入、服务/用户内容审核、举报及获授的售后处理 | 业务本身需要审核的功能仍存在，由一个有权限的运营执行，不额外加第二审核人 |
| 运营管理员 | 经营治理、处罚/下线、获授的交易异常及配置 | 执行已授权动作，不建立复核队列；权限管理仍须相应权限，不因“管理员”称谓自动等于超管 |
| 财务只读 | 原有财务台账的查询及获准导出 | 默认只读；确需已有业务执行动作时通过RBAC显式配置，不另外建财务执行系统。实际权限由配置决定，UI须显示真实授权，名称不替代检查 |
| 审计只读 | 日志/留痕查询及获准导出 | 日志不可篡改/删除，任何角色都不能获授修改历史审计的能力 |
| 平台超级管理员 | 全部已批准业务权限、账号/角色管理、全平台范围 | 无需第二账号复核；不能创造V1未批准动作或绕过不可变规则 |

原权限矩阵中的▲不再表示审批：对于既有已批准动作，改为“具备该动作权限可单人执行”；—不自动开放，○仍表示默认查看，●需由后台动作权限支撑。权限管理可以由超管直接配置；不将所有普通角色自动升级全权。

## 3. 取消什么、保留什么

- 取消后台内部双人/多级审批、禁止本人复核、第二操作人必填、第二管理员解锁、双人权限变更等需求。不得在接口里留下强制secondApprover/reviewer账号作为生效条件。
- 运营编辑自己的平台内容/公告可直接发布；商家入驻、服务审核、用户发布内容审核等既有业务动作不因“无内部审批”而自动全部通过。它们由单个获授权运营处理。
- 高风险操作原有同一人二次确认、填写原因/用途、服务端校验、审计留痕保留；同一人确认弹窗不是双运营审批。敏感信息仍需对应授权与用途并留痕，但不新增第二人审批步骤。
- “运营无审批”不绕过支付渠道、签约Provider或外部机构的实际业务校验，也不取消退款申请的商家处理、渠道回调与最终结果。
- 超管及其他获授权账号都不能正常代商家接单、修改渠道事实金额、手工标记资金到账、代商家提现、篡改审计或恢复失效旧售后；封板SSOT的退款/核销互斥和售后终局规则不变。
- 资金冻结/分账/提现/保证金是否进入本期的未决范围仍由OD-W0-001处理；本裁决没有新增或删除这些业务范围。RBAC能分配的只能是已经批准存在的动作。
- 全平台数据范围不等于敏感字段无条件明文；默认脱敏、受控查看/导出、用途与审计仍执行既有规定。

## 4. 任务与验收

AUTH-001建立角色/动作/数据范围的技术映射，A-001只建立通用壳，后续运营业务Issue接入真实服务端鉴权。详细权限码/DTO/账号授权持久化经CCR-PERM-001制定，不扩大Issue或假定接口已经实现。默认矩阵按原PRD执行上述确定性转换，不再要求CTO重审相同的单运营选择。

| ID | 验收场景 | 预期 |
|---|---|---|
| PERM-001 | 单个有裁决权限运营处理售后 | 无第二账号/审批环节，首次正式结论生效；仍校验资格与refund/verify竞态 |
| PERM-002 | 一个超管修改权限/一个获权运营执行原▲动作 | 不创建内部审批任务、不要求复核人；原原因、幂等、确认及审计要求有效 |
| PERM-003 | 运营编辑发布获权平台内容/公告 | 可直接发布；没有内部待审批拦截；商家/用户内容业务审核不被自动取消 |
| PERM-004 | 超管访问已批准模块及跨城市/商家数据 | 默认全业务动作/全平台范围；仍不能越过业务硬规则和敏感字段约束 |
| PERM-005 | 普通/财务账号未授予与已授予某现有动作 | 后端按实际RBAC允许或403拒绝，不按角色名称放行，不出现新增财务流程 |
| PERM-006 | 单人操作及被拒绝访问后检查审计 | 记录实际操作人/结果，日志不可修改；不把缺少第二人记作失败 |
