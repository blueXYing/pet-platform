# 售后流程人工裁决补充 v1.0

日期：2026-09-30。状态：APPROVED。用户原话：**“批准四项推荐规则及 A1–A3”**。来源为本聊天四项问题与[已审阅总案](../../planning/ccr/CCR-W2-API-001/aftersale-workflow-proposal.md)。覆盖旧PRD/草案与下列规则冲突的解释，不代表功能已经交付。

1. **P1，一单一活动工单。** 同订单同时仅PENDING/PROCESSING/WAITING_SUPPLEMENT之一的单笔工单；其他新问题追加当前工单，不另开并行活动工单。
2. **P2，终局前可撤回。** 本人可在上述活动状态撤回。仍满足原资格且在原七天内可重新申请，使用新工单编号，保留旧证据、记录及原时限；不重开旧工单、不刷新七天。
3. **P3，普通退款与活动售后双向互斥。** 普通申请PENDING_MERCHANT或APPROVED/AUTO_APPROVED尚未建退款单时，不能新建AFS；活动AFS期间不能新建普通退款申请。拒绝、撤回等结束后按各自原资格切换。已存在refund_order继续执行一单一次退款和禁止再申请规则，不因渠道UNKNOWN/FAILED重获资格。
4. **P4，终局后新问题由运营核对。** 已有非退款终局，用户可在原资格和原窗口内提交新问题说明。服务端关联历史终局，运营受理前核对说明与历史；确属新问题才受理。重复问题关闭并引用原结论，不产生第二个决定、不改旧结论、不创建退款。不得凭问题类型或描述相似度自动判定。核销后合法新问题仍遵循核销起算七天。

具体技术映射：最终裁决使用RESOLVED；重复问题仅PENDING→CLOSED，原因DUPLICATE_FINAL_PROBLEM及真实同单既有非退款终局引用。WITHDRAWN/INVALIDATED或无决定的重复关闭不是正式终局。Create/Accept的新问题说明/核对及历史集合版本持久留痕；不引入二次复审、MFA或内部双人审批。

七天包含截止等号，沿Scheduler09 §33：数据库UTC毫秒 `anchor <= now <= anchor + 7*24h`。已核销anchor=真实verifiedAt；未核销已开始且有真实商家拒绝anchor=appointmentStart，不取拒绝时间。七天仅限制发起，不限制既有工单裁决完成时间。运营指定补证截止，提交满足该轮须严格早于截止；截止及之后只按超时恢复处理中，不自动裁决。

A1–A3批准范围：真实内部售后工作流、运营五类终局与可信FULL/PARTIAL来源、原子退款建单、历史核销兼容及真实数据库并发验收，相关正式契约/Schema/事件/任务/必要多模块适配、隔离测试及PR。退款型裁决、refund_order、ORDER绑定、事件任务和首回执同事务；核销先成功旧未履约工单失效，退款先建单禁止后核销。

OD-W0-001资金权威基线仍独立缺失。缺真实资金资格适配时退款型终裁及首次出款失败关闭，测试专用资金Provider不代表生产可退；不自行实现资金冻结/分账/追回。非退款流程可以独立验收。默认关闭，不授权PR合并、生产迁移或启用。员工绑定、REF-001、公开HTTP/前端、通知真实送达及券/积分/评价消费者保持各自范围。
