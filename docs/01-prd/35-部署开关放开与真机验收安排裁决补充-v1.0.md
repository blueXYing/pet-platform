# 35号 部署开关放开与真机验收安排裁决补充 v1.0

状态：已批准执行（用户 2026-10-16 裁决）。本文如实记录两条裁决与执行口径，不添加用户未裁决的内容。

## 一、裁决原文要点

1. **平台能力开关全部放开（默认开启），与发版解耦**。能力是否可用不再等待"发版动作"，部署即默认开启。
2. **真机验收延后至正式上线前**。原与开关放开绑定的真机验收安排取消，改到正式上线前统一执行。
3. 若个别开关放开有**真实卡点**，列清单回报，由主会话转用户裁决；未裁决前维持现状（保持默认关闭）。

## 二、执行口径（翻转门槛）

对全仓 `pet.*.enabled` 布尔开关逐一定义装配语义后，按以下门槛执行翻转：

- **A 类（翻默认开启）**：装配期不硬性要求平台无法自给的第三方凭据。翻转方式为 `application.yml` 默认值 + 装配类 `@ConditionalOnProperty(matchIfMissing)` 同步翻转（多键组合条件除外，见 §四.3）；fail-closed 语义不丢：运行期缺依赖仍然 503 失败关闭，原有"关了就拒绝"的测试改为显式关上下文保留。
- **B 类（保持默认关闭，列卡点）**：装配期（boot）硬性要求第三方凭据或部署显式提供的基座，放开后无凭据即启动失败（装配 guard 的 fail-fast 设计使然），不属于"缺凭据运行期失败关闭"。逐项列 §三卡点清单。
- **C 类（保持，列依据）**：测试专用或被其他裁决/安全缺省钉死。

基线：origin/develop（含 PR#165~#178），契约零变化（OpenAPI11 operationId 计数保持 204，本文档不改任何 Contract/Schema/Event，不改 ISSUE_CATALOG）。

## 四、B 类保持清单与卡点（大白话）

总口径：以下开关一开，**启动期**就要平台给不出的第三方凭据/基座；现在的装配 guard 会直接拒绝启动（这是文档化的 fail-fast 设计，不是故障）。在卡点解除前保持默认关闭。

### 1. 部署基座（一切能力的前提）
- `pet.auth.admin.enabled`（含 migration/maintenance）：缺什么——**三把自签会话密钥**（key-id/mac/encryption，平台自己生成即可，不是第三方的）、Redis 地址、审计文件路径、HTTPS 或回环 origin。放开后会发生什么——不配就启动失败。它是全平台 ID 提供器（Snowflake）的唯一来源，任何部署都必须先配它，配好它之后上面 A 类全部自动生效。

### 2. 微信小程序会话（C 端一切路由的总闸）
- `pet.auth.c.enabled`：缺什么——**微信小程序 app-id/app-secret（真实凭据）**+ Redis。放开后会发生什么——不配微信凭证直接启动失败；配了桩值可以起但真机登录不了。它同时是 C 端全部路由安全链的总闸，真机验收延后与此绑定。

### 3. 交易与退款资金链（拉卡拉）
- `pet.payment.foundation.enabled`：支付事实/绑定/回执底座。缺什么——运行期需要拉卡拉回调验签证书（缺省验签失败关闭，可启动但支付回执永远过不了）+ 商户绑定表配置。放开后会发生什么——能启动，但支付回调全部验签失败关闭，等于半开。
- `pet.payment.dispatch.enabled`：真实拉卡拉支付发起。缺什么——**完整拉卡拉商户凭证**（environment/appId/商户序列号/商户私钥 PEM/平台证书 PEM/参数密钥文件/回调地址）。放开后会发生什么——缺任一即启动失败（"Dispatch settings unavailable"）。
- `pet.refund.late.enabled`(+worker)、`pet.order.merchant.enabled`(+http/worker)、`pet.order.auto-confirm.*`、`pet.order.reschedule.*`、`pet.verification.credential.*`(+completion/http)、`pet.refund.application.*`(含 merchant.http)、`pet.aftersale.*`、`pet.admin.trade.http/worker.enabled`：缺什么——**拉卡拉退款 RSA 凭证**（只要接单/售后/处置任一域打开，退款执行渠道装配就会要求商户私钥+平台证书，缺了启动失败）+ 微信会话（refund.application/aftersale 的 guard 硬性要求 auth.c）+ 各自的保护密钥（protection-key/credential 三密钥/退款 reason-codes 白名单/售后批准目录）。放开后会发生什么——逐级启动失败，错误信息会点名缺的开关或凭证。
- 以上域同受 F-1 互锁约束（outbox+payment.foundation+接单/售后/迟到退款任一 → refund 渠道必须可装配），详见 21号 §2.1。

### 4. 素材与扫描（OSS / ClamAV）
- `pet.merchant.application.enabled`：入驻申请内核。缺什么——**OSS 私有素材通道（private-assets）+ 法人主体/受保护值自签密钥端口**（入驻上传身份证等材料走 OSS，装配期硬依赖这三个 bean/端口）。放开后会发生什么——缺任一端口启动失败。其站内通知 consumer 已随 A 类放开，内核与 OSS 一并配齐后即可开。
- `pet.private-assets.enabled`：缺什么——**OSS 连接环境变量** + 授权/理由密钥（PRIVATE_ASSET_GRANT/REASON_*）。放开后会发生什么——能启动，上传/授权请求 503 失败关闭。
- `pet.service.cover-signing.enabled`：缺什么——真实 S3/OSS 直传环境 + 必须与 private-assets 同开。放开后会发生什么——缺环境启动失败或签名 503。
- ClamAV 扫描（私有素材病毒扫描）：无独立布尔开关，随 private-assets 装配；缺 ClamAV 服务时扫描失败关闭。

### 5. C 目录读族 / 排期读写 / 收藏足迹（装配链硬依赖入驻内核）
- `pet.service.query.enabled`、`pet.store.query.enabled`、`pet.schedule.query.enabled`(+selection)、`pet.service.command.enabled`、`pet.schedule.command.enabled`(+http)、`pet.favtrack.http.enabled`：缺什么——**装配期硬链 `MerchantDisplayEligibilityApi`/`ApplicationReviewFactsReader`/`MerchantAdmissionQueryApi`/`ServiceQueryApi`，全部由入驻申请内核（`pet.merchant.application.enabled`，OSS 门槛，见 §四.4）提供**。放开后会发生什么——入驻内核不配齐就启动失败（CAddressHttpTest/CEncyclopediaHttpTest 实测复现）。它们随入驻内核+OSS 一并放开。
- 运营台读面 `pet.admin.governance.http.enabled` 已放开；**`pet.admin.ops.http.enabled` 列为"待修复后再开"（E2E 取证 FA-2，启动失败）**：AdminOpsController 按类型注入 encyclopedia/coupon 双面 API，而内核是同实现双 bean（无 @Primary/限定符），标准整机启动即注入歧义失败；另有 FA-1/FA-3（63号处置 POST 与 65号 ops 读路由在安全链无放行条目，翻开后 403）。修复批合入前保持默认关闭。

### 6. 真实通知投递
- `pet.notification.delivery.enabled`：缺什么——**真实微信订阅消息适配器**（部署提供 bean+模板凭据）。放开后会发生什么——能启动，投递任务全部失败关闭（UnconfiguredWechatDeliveryAdapter）。站内通知（A 类已放开）不受影响。

### 7. 其他
- `pet.merchant.staff-member.enabled`：缺什么——主装配树当前**没有注册 `UserPhoneVerificationApi` bean**（须由部署提供），另需排期保护底座与 auth.c。放开后会发生什么——启动失败（bean 注入失败）。
- `pet.merchant.subject.enabled` / `pet.merchant.protection.enabled`：缺什么——法人主体与受保护值加密的**密钥环境变量**（且密钥独立性校验）。放开后会发生什么——缺密钥启动失败。
- `pet.review.enabled`(+http/appeal)：缺什么——guard 硬性要求 auth.c（微信凭证）。放开后会发生什么——启动失败。
- `pet.review.appeal.http.enabled` / `pet.refund.merchant.http.enabled`：面开关钉在上述 B 类内核上（越级开=启动失败），随内核一并放开。
- `pet.refund.late.worker.enabled`：随 refund.late。

## 六、与既有文档的关系

- 21号《部署开关组合清单》默认值列按本裁决同步更新，三档推荐组合中"保持(false)"的项以本文 §三/§四 为准；装配依赖与 §2 矩阵不变。
- 契约零变化：OpenAPI11 不改（operationId 计数 204 不动），`x-implementation-status` 注记的"DEFAULT_OFF"描述以本文为缺省值勘误；10号/各 Contract 的路由与语义不变。
- ISSUE_CATALOG 不改（本裁决不改任何 Issue 范围）。
- 真机验收安排：延后至正式上线前统一执行，原验收计划中与开关放开绑定的时间点作废。

## 七、遗留风险（如实披露）

1. B 类未放开前，交易闭环止步于"下单占位→10 分钟自动关闭"：接单、核销、退款、售后、真实支付在部署上仍需按 §四配齐凭据后逐域放开（装配 guard 会点名缺什么）。
2. 运营台（65号）20 条路由在当前 admin 安全链中没有对应 permitAll 段（链上仅登记了 trade/governance/aftersale/appeal/points-task-config 等）；`admin.ops.http` 放开后内核装配正常，但标准启动形态下这些路由在 Spring Security 层仍会被 denyAll 拒绝。这是 65号合入时已存在的接线问题，不在本裁决修复范围，已单独披露待主会话确认。
3. `matchIfMissing` 翻转后，"从 yml 删除某 A 类开关行"不再等于关闭该能力（缺省=开）；显式写 `false` 才是关闭。运维文档需知悉。
4. A 类翻转影响全部整机启动形态的测试夹具（E2E/live server 会多装配若干内核 bean）；已按"显式关上下文"修钉默认关的测试，全部测试绿后再合入。
