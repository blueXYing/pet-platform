# 宠物平台 V1.0 产品裁决与 SSOT 基线（迟到支付自动退款规则封板）

> 本文档用于统一 C 端、商家端、运营端三端产品规则，作为后续 PRD 修订、研发设计、测试验收和状态机实现的统一依据。  
> 本文档内容基于当前已确认的产品裁决整理，后续若有新决策，应优先更新本 SSOT，再同步修改三端 PRD。

---

## 一、V1.0 产品裁决总表

| 领域 | V1.0 最终规则 |
|---|---|
| 商家接单 | 支付成功进入 `待确认`，商家 **30 分钟**未处理自动接单 |
| 订单编号 | 订单号、退款单号统一采用 **Snowflake ID**；不再使用日期+随机码等格式 |
| 支付渠道 | 拉卡拉作为第三方支付服务商 |
| 小程序支付 | 小程序直接微信支付，不展示支付渠道选择 |
| App 支付 | 后续 App 支持微信支付 / 支付宝 |
| 支付密码 | 不做平台支付密码 |
| 登录 | 小程序支持微信快捷登录、手机号验证码、手机号密码；App 后续支持手机号验证码、手机号密码 |
| 首次验证码/微信注册 | 不自动生成密码；未设置密码时密码登录统一返回账号/密码错误，用户自己重置密码 |
| 履约方式 | 只有 `到店`、`上门/接送` 两种，不存在“无需履约” |
| 服务形态 | V1.0 **只做单次服务**；套餐、次卡、普通商品均不做 |
| 直接售卖 | 删除“直接售卖/立即购买”模式 |
| 预约要求 | 到店、上门服务 **都必须预约** |
| 接送约束 | 送回时间开始 ≥ 上门时间开始 + **120 分钟** |
| 排期粒度 | 商家自定义预约时间，**精确到分钟**；不做固定 60 分钟全平台槽位 |
| 周排期模板 | 不做“周一～周日 7 天循环模板” |
| 容量 | 实际可预约容量 = `min(商家配置容量, 当前可用服务人员数量)` |
| 服务人员 | V1.0 用户不能选人，由商家指派 |
| 改期 | 每单最多 1 次；预约开始前；同商家、同服务；改期后重新进入 `待确认` 并重新计算 30 分钟 |
| 评分 | 单条得分：门店 40% + 服务 40% + 人员 20%；近 12 个月有效评价算术平均，保留 1 位小数；不足 5 条显示“暂无评分” |
| 商家/运营核销率 | 两套指标独立存在，不强制统一 |
| 第三方团购 | V1.0 做美团/大众点评核销；独立于平台订单、支付、退款、GMV |
| 商家下线 | 允许运营立即下线；停止新订单，**存量订单继续履约** |
| 运营代接单 | 不允许正常运营代接单 |
| 运营异常处置 | 门店下线、资质失效、商家失联等特殊情况，运营可异常处置订单 |
| AI 客服 | V1.0 不做 |
| 人工客服 | V1.0 做 |
| 用户私信 IM | V1.0 不做 |
| 黑名单 | 仅预留，不开发完整能力 |
| 直播 | V1.0 **不做，也不预留** |
| 积分 | 做签到、邀请、任务、下单奖励、余额、流水；不做积分抵现、积分商城、兑换 |
| C 端消息中心 | 保留 |
| 商家消息中心 | 保留 |
| 社区互动通知 | 保留点赞、收藏、关注、评论/@ 等 |
| 外部通知 | 站内通知之外，同时做微信侧外部通知；具体公众号/订阅消息接入形态后续按实际微信账号能力落技术方案 |
| 强制通知 | 订单、退款、核销、售后、审核必须保留站内消息；只能关闭外部推送 |
| 评价申诉 | 每条评价最多申诉一次 |
| 售后复审 | **没有复审机制**，运营首次裁决即最终裁决 |
| 支付超时关闭后的迟到支付 | 若平台已因支付超时关闭订单，但随后收到渠道确认的真实支付成功事实，**不恢复订单，系统自动按渠道实际支付金额发起全额原路退款**；原订单保持关闭，不恢复预约，不重新占用优惠券，不进入接单/履约流程 |

## 二、最终订单主状态

现有旧 PRD 的“八态”不再适用，V1.0 主状态建议统一为：

```text
待支付
待确认
待服务
已完成
已取消
退款待确认
退款中
已退款
部分退款
售后
```

其中：

- `退款待确认`：仅用于预约开始后，需要商家处理退款的场景。
- `部分退款`：运营售后裁决产生的正式终态。
- `售后`：订单关联售后工单处于处理中时的业务状态。

## 三、正常预约履约状态机

```text
创建订单
  ↓
待支付
  ↓ 支付成功
待确认
  ├─ 商家30分钟内接单
  │      ↓
  │    待服务
  │
  ├─ 30分钟未处理
  │      ↓
  │   自动接单
  │      ↓
  │    待服务
  │
  └─ 商家拒单
         ↓
       退款中
         ↓
       已退款
```

### 改期规则

```text
待确认 / 待服务
      ↓
预约开始前申请改期
      ↓
先锁定新时间
      ↓
成功后释放原时间
      ↓
待确认
      ↓
重新开始30分钟确认周期
```

约束：

- 每笔订单最多改期 1 次。
- 必须是同一商家、同一服务。
- 仅允许在预约开始前改期。
- 改期成功后重新进入 `待确认`。
- 改期后重新计算 30 分钟自动接单倒计时。

## 四、退款状态机

### 4.1 预约开始时间之前

条件：

```text
当前时间 < 预约开始时间
```

流程：

```text
买家申请退款
      ↓
无需商家确认
      ↓
创建退款单成功
      ↓
立即禁止核销
      ↓
退款中
      ↓
拉卡拉退款成功
      ↓
已退款
```

规则：

- 服务开始前属于系统自动退款。
- 不进入 `退款待确认`。
- 退款单创建成功后立即禁止核销。
- 槽位只在支付渠道退款最终成功后释放。

---

### 4.2 预约时间已到，但尚未核销

条件：

```text
当前时间 >= 预约开始时间
订单状态仍为待服务
```

流程：

```text
买家申请退款
      ↓
退款待确认
      ↓
商家24小时内处理
```

商家处理结果只有两种：

#### 同意全额退款

```text
同意全额退款
      ↓
创建退款单成功
      ↓
禁止核销
      ↓
退款中
      ↓
已退款
```

#### 拒绝退款

```text
拒绝退款
  ↓
必须填写拒绝原因
  ↓
原因展示给买家
  ↓
恢复待服务
  ↓
买家可发起售后
```

#### 商家超时

```text
退款待确认
      ↓
24小时未处理
      ↓
系统自动全额退款
```

---

### 4.3 已核销完成后的退款

```text
已完成
  ↓
买家申请退款
  ↓
退款待确认
  ↓
商家处理
```

商家只有两种选择：

```text
同意全额退款
或
拒绝退款
```

商家无权直接做部分退款。

如果商家拒绝：

```text
商家拒绝
  ↓
填写原因并展示买家
  ↓
订单恢复已完成
  ↓
买家仍有异议
  ↓
申请售后
```

## 五、售后状态机

售后最终裁决权归运营端。

```text
买家发起售后
    ↓
待处理
    ↓
运营受理
    ↓
处理中
    ↓
必要时待补充
    ↓
运营裁决
```

运营可以裁决：

```text
全额退款
部分退款
驳回
重新服务
其他非退款处理
```

规则：

- 售后裁决后不再支持二次复审。
- 运营首次裁决即最终裁决。
- 商家可以提供说明、证据、意见，但不是最终裁决方。


### 6.2 已到预约时间但未核销

条件：

```text
预约时间已到
+ 商家拒绝退款
```

则：

```text
预约开始时间起 7 天内
→ 可以发起售后
```

## 七、未核销订单的“售后 × 核销 × 退款”并发规则

这是 V1.0 最关键的并发规则之一。

### 7.1 售后期间允许继续履约

```text
待服务
  ↓
商家拒绝退款
  ↓
买家发起售后
  ↓
售后处理中
```

在**退款单真正创建成功之前**：

> 商家仍然可以继续履约并扫码核销。

---

### 7.2 核销先成功

```text
售后处理中
      ↓
商家核销成功
      ↓
当前未履约售后
→ 已撤销 / 已失效
      ↓
禁止运营继续基于该工单退款
      ↓
订单 → 已完成
      ↓
重新开启核销后7天售后窗口
```

说明：

- 原“未履约”类售后自动失效。
- 买家可以基于服务完成后的新问题重新发起售后。
- 新售后时效重新从核销成功时间起算 7 天。

---

### 7.3 退款单先创建成功

```text
售后处理中
      ↓
运营裁决退款
      ↓
退款单创建成功
      ↓
立即禁止核销
      ↓
退款中
```

---

### 7.4 技术并发原则

以下两个动作必须互斥：

```text
核销成功
退款单创建成功
```

产品优先级规则：

```text
核销已成功
→ 当前未履约售后立即失效
→ 禁止再裁决退款

退款单已成功创建
→ 立即禁止核销
```

## 八、部分退款规则

部分退款只能由运营售后裁决产生。

```text
运营裁决部分退款
      ↓
创建退款单
      ↓
退款成功
      ↓
订单状态 = 部分退款
      ↓
订单业务结束
```

规则：

- 一笔订单最多只允许一次退款。
- 部分退款后不能再次发起新的售后。
- 已核销后发生部分退款的订单仍允许评价。
- 评价窗口统一从**核销成功时间**起计算 30 天。
- 评价正常公开展示。
- 但已核销后发生部分退款的评价 **不参与星级统计**；未核销部分退款不产生评价。
- 未核销即发生部分退款的订单 **不允许评价**。

不计入：

```text
门店综合评分
服务评分统计
服务人员评分统计
```

因此技术上建议评价记录保留类似：

```text
score_included = true / false
```

用于区分：

- 是否展示评价
- 是否计入评分模型

## 十、积分规则

V1.0 只做：

```text
签到积分
邀请积分
任务积分
下单奖励积分
积分余额
积分流水
```

V1.0 不做：

```text
积分抵现金
积分抵扣订单
积分商城
积分兑换
```

### 10.1 退款后的下单奖励积分扣回

不是“返积分”，而是：

> 按退款比例扣回本订单已经奖励给用户的积分。

示例：

```text
订单奖励 = 101积分
退款比例 = 50%

101 × 50% = 50.5
四舍五入 = 51积分

最终扣回 51 积分
```

规则：

- 全额退款：扣回全部本单奖励积分。
- 部分退款：按退款比例扣回。
- 取整规则：四舍五入。

## 十一、评分与评价规则

### 11.1 商家评分算法

单条评价综合分：

```text
门店评分 × 40%
+
服务评分 × 40%
+
人员评分 × 20%
```

汇总规则：

```text
近12个月有效评价算术平均
保留1位小数
有效评价 < 5条 → 显示“暂无评分”
```

### 11.2 部分退款评价

```text
已核销后发生部分退款：
- 允许评价
- 评价窗口从核销成功时间起计算30天
- 允许公开展示文字/图片
- 不参与任何星级/综合评分统计

未核销即发生部分退款：
- 不允许评价
```

### 11.3 评价申诉

- 商家可以对违规评价发起申诉。
- 每条评价最多申诉一次。
- 评价申诉与售后复审是两个概念。
- 售后没有复审，但评价申诉仍保留。

## 十二、排期与容量规则

### 12.1 时间槽

V1.0：

```text
商家自定义可预约时间
精确到分钟
```

不做：

```text
固定60分钟槽位
统一平台槽位长度
周一～周日循环模板
```

### 12.2 容量

```text
实际可预约容量
=
min(
  商家配置容量,
  当前可用服务人员数
)
```

示例：

```text
商家设置最大容量 = 5
当前可用服务人员 = 3

实际可预约容量 = 3
```

# 十九、三份 PRD 修改清单

# 二十二、迟到支付成功自动退款

已封板：

```text
订单因支付超时关闭
↓
平台已释放预约资源与待支付阶段冻结权益
↓
随后渠道确认真实支付成功
↓
原订单保持关闭
↓
系统自动创建全额退款单
↓
按渠道实际支付金额原路退款
↓
退款成功后展示已退款
```

规则：

- 不恢复原订单到待确认/待服务。
- 不要求用户重新选择预约时间。
- 不重新占用已经释放的预约资源。
- 不抢回、不重新冻结已经释放的优惠券。
- 即使该优惠券后来被用户用于另一笔订单，也不影响迟到支付退款。
- 退款金额以该笔渠道真实支付成功金额为准。
- 不创建第二张业务订单。
- 一笔订单仍最多一张业务退款单，渠道查询/重试不算第二次业务退款。
- 若退款渠道结果未知，订单展示 `退款中`，持续查单，直到获得最终结果。
- 迟到支付不得触发正常 `OrderPaid` 履约链路，不进入 30 分钟商家接单。
- 该场景无需再处理恢复预约、优惠券冲突、改期额度或补差价等恢复性问题。

# 三十一、预约与订单人员保护联合裁决（2026-09-24，人工批准）

用户明确批准[ROC-1～6 六项联合推荐](../../planning/ccr/CCR-W2-API-001/reservation-order-protection-decisions.md)，详细契约见[36号预约与订单人员保护](../04-api/36-Reservation-Order-Protection-Contract-v0.1.md)。员工基础管理门槛见 §30；本裁决不改写其读写门槛。此处覆盖旧提案中的“待批准”，不改变 §3/§12/§13/§29 的单次必须预约、分钟级非固定槽、配置容量与可用人员取小、用户不选人、商家指派及返程开始至少晚 120 分钟。

- 同门店所有相关服务的预约与人员占用要作完整可行性证明，不能让同一员工被两笔重叠预约重复计算。已有商家最终指派必须固定；未指派单只作内部数学匹配，不自动写订单指派、不向用户展示。原窗口配置容量也须逐段成立；事实不全或证明超预算时失败关闭。
- 一笔接送订单最终由**同一名**商家指派员工覆盖所选 PICKUP 与 RETURN 两个完整窗口；两个窗口之间不要求持续排班。上门/返程仍分别选窗，返程开始 ≥ 上门开始 +120 分钟，不从固定 60 分钟或服务时长推两窗结束。
- 新到店预约采用一条同店同服务 OPEN GENERAL 原窗，完整容纳由**既有到店服务时长规则**确定的实际预约区间；跨相邻 GENERAL 窗的新单不能提交。GENERAL claim 保留原窗 ID 与实际区间。存量跨窗单继续履约、逐单核对，不自动取消或伪造占用。这是本次新批准的单窗产品选择，原到店时长规则不变。
- ORDER 预生成非空 orderId，SCH hold 与 ORDER 主单创建在同一顶层主库本地事务双向绑定；失败整体回滚，外部支付在提交后。ORDER 必须提供同事务按预约及按员工/门店的当前指派完整性事实，已 RELEASED 的预约不能让仍在途的指派从减员检查中消失；不一致时失败关闭。
- 已有商家当前指派的订单改期，保留该人员并检验其是否覆盖新实际区间或接送两个完整窗；不能覆盖则改期失败，原预约、claim、指派、改期次数与确认周期保持。不得自动撤派或暗中改派。原有改期最多一次、同商家同服务、预约开始前、先锁新失败留旧规则继续有效。

ROC-1～6 已批准为合同，**尚未实现**。原共同门店锁、能力集合版本、接送两 claim 与旧 GENERAL 隔离按已批 SCHC-1～4 保持；06/07/10/11 的实际接口与 Schema、迁移和 MySQL 并发测试须在后续切片交付。此批准不含 PR 合并、生产迁移/开关、固定业务上限或任何 V1 范围外能力。
